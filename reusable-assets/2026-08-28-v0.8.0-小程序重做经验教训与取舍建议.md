# 教师工作台 v0.8.0 小程序重做经验教训与取舍建议

## 一、最重要的判断

自动化测试通过不等于微信小程序可用。Node 测试可以验证字符串契约、云函数逻辑和页面文件存在，但不能替代微信开发者工具对 WXSS 编译、页面注册、真实路由、CloudBase 身份和文件 API 的验证。

以后必须把“可编译、可启动、可导航、可读数据、可写数据、真机操作”分成独立验收门槛，任何一项未验证都不能称为完成。

## 二、本次暴露的问题

1. 把客户端功能清单直接映射成小程序页面，页面数量快速增加，但没有先完成一个真正可用的纵向闭环。
2. 过早进行全局 UI 重构，样式令牌、页面级样式和重复选择器叠加，增加了 WXSS 编译和移动端排版风险。
3. 修改文件时曾把补丁标记文本写入 WXSS，说明需要在提交前加入源文件污染扫描。
4. 开发者工具项目根目录、worktree 和缓存没有在每次验收前固定核对，导致旧日志与当前源码混淆。
5. 云函数已部署、管理端冒烟成功，只能证明入口和认证保护存在，不能证明微信身份下的真实业务闭环。
6. `env.js` 被忽略且没有强制配置检查；新机器或新 worktree 可能静默回退到占位环境，造成“页面能打开但业务不可用”。
7. 设计文档中“已接入”“已完成”“已验证”边界不够严格，阶段性页面骨架容易被误解为客户端功能等价完成。

## 三、重做时应保留的原则

- 桌面客户端是业务行为基准，小程序只改变布局、步骤和控件形态。
- 所有业务记录使用同一套稳定 UUID、字段、状态和关联关系。
- 云端始终从微信上下文取得所有者身份，客户端传入的 `ownerId` 不能作为授权依据。
- 导入采用 `precheck → preview → commit`；备份恢复先生成快照，写入操作必须可追踪、可回滚或可恢复。
- 默认软删除，带修订号；重复导入使用源导出 ID 做幂等保护。
- 先做脱敏测试数据集，再做真实微信身份验收；禁止用真实业务数据反复试错。
- 先完成“身份 → 数据集 → 班级 → 学生列表/详情”的最小闭环，再扩展业务模块。

## 四、重做时应舍弃的做法

- 不要直接复制当前 `miniprogram/pages/` 作为生产模板。
- 不要把“页面文件齐全”当成功能完成。
- 不要把状态检查函数称为双向同步。
- 不要在没有微信开发者工具证据时声称“移动端已验收”。
- 不要在页面中直接拼接复杂云函数和数据权限逻辑。
- 不要为了赶进度同时改导航、全局样式、数据契约和云函数；每次只改变一个边界。

## 五、推荐的新实施顺序

1. 从稳定桌面端分支创建全新小程序分支。
2. 先建立最小原生小程序壳，并在微信开发者工具中确认无编译错误。
3. 接入 CloudBase 环境检查和微信身份状态页；未配置时必须显示明确错误。
4. 完成数据集/班级选择和只读学生列表，使用脱敏数据做真实点击验收。
5. 完成学生新增、编辑、软删除和详情闭环，再迁移考勤、请假、成绩等模块。
6. 每个模块都执行：桌面端字段核对 → 云函数契约 → 页面实现 → 空/错/无权限状态 → 自动化测试 → 微信工具验收。
7. 最后实现完整备份、Excel 文件交换和真正双向同步；同步必须另立设计和冲突测试，不复用当前状态检查接口的名称。
