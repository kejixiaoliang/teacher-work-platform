# Web 与桌面版功能统一设计

日期：2026-08-05  
目标版本：`0.2.0`

## 1. 背景与问题

当前项目的 Web 原型以 `master` 分支为基准，Windows 绿色便携版由 Tauri v2 封装同一套 Vue 前端。产品不应被理解为两套独立应用：Web 与 EXE 应共享页面、业务规则、接口类型和版本号，只允许在运行环境能力上存在适配差异。

目前已经确认一个跨环境差异：座位管理使用 HTML5 原生 `dragstart / dataTransfer / drop` 完成拖拽。该方式在普通浏览器中可用，但在 Tauri 的 Windows WebView2 环境中表现不稳定，导致 EXE 版不能可靠拖动学生换座。虽然现有页面提供“先点击源座位，再点击目标座位”的备用操作，但主要交互仍未达到 Web 与 EXE 一致。

项目还存在版本来源分散的问题：`package.json`、Tauri 配置和 Cargo 当前都写有 `0.1.0`，应用内更新日志则使用日期版本。继续人工维护容易产生 EXE、ZIP、README、更新日志和 Web 页面显示不一致。

## 2. 产品原则

1. 只维护一套 Vue 页面和业务代码。
2. `master` 最终成为 Web 与桌面版的唯一产品源码基线。
3. Web 与 EXE 使用相同的后端路由、数据库结构和业务规则。
4. 环境差异只能进入明确的运行时适配层，不能复制业务页面。
5. 同一项功能必须在 Web 与 Release EXE 中得到相同的数据结果和用户反馈。
6. 开发服务器能运行不代表桌面版完成；最终 ZIP 解压运行验证仍是桌面交付门禁。

## 3. 目标架构

```text
同一套 web/src 页面、组件、领域规则和 API 封装
                       │
             运行时配置与 desktopApi
                       │
        ┌──────────────┴──────────────┐
        │                             │
Web Runtime                     Desktop Runtime
浏览器 + Web 后端               Tauri + 内置本地后端
        │                             │
        └──────相同接口与业务结果──────┘
```

共享范围包括：

- Vue 页面、组件、样式和交互规则；
- 前端 API 类型与错误处理；
- Express 路由与数据库访问；
- 数据验证、导入导出和领域算法；
- 自动化测试中的业务行为用例。

适配层只处理：

- API 基地址和临时鉴权 token；
- Web 与 Tauri 的启动方式；
- 本地文件、资源目录和数据目录定位；
- 桌面窗口、退出和内置后端生命周期；
- 仅桌面环境存在的 Windows 限制提示。

不得在适配层重新实现学生、座位、考勤、成绩等业务逻辑。

## 4. 座位拖拽统一方案

### 4.1 根因

当前 `Seats.vue` 在 `master` 与 Tauri 分支中完全相同，说明问题不是桌面版漏复制代码。差异来自 HTML5 原生拖放事件对 WebView2 的依赖，尤其是 `dataTransfer` 在嵌入式 WebView 中不能作为稳定的应用内移动状态载体。

### 4.2 新交互

核心拖动改为 Pointer Events，Web 和 EXE 使用同一实现：

1. 在手动模式下按住有学生且未锁定的座位，记录源座位和指针 ID。
2. 指针移动超过小幅阈值后进入拖动状态，避免普通点击被误判为拖动。
3. 使用元素命中或座位数据属性确定当前目标座位并显示高亮。
4. 松开指针时调用现有 `moveSeat(sourceKey, targetKey)`。
5. 目标为空座时移动学生；目标有人时交换学生。
6. 源座位或目标座位锁定时拒绝操作并提示原因。
7. 成功后标记布局为未保存，并保留现有“保存布局”流程。
8. `pointerup`、`pointercancel`、组件卸载和模式切换都必须清理拖动状态。

### 4.3 兼容与备用操作

- 保留“点击学生座位，再点击目标座位”的移动/交换方式。
- 保留右键菜单、座位安排弹窗和键鼠点击操作。
- Pointer Events 同时覆盖鼠标、触控板和未来可能使用的触屏。
- 不再把 HTML5 `dataTransfer` 作为核心状态；可以删除旧拖放事件，避免两个机制互相触发。
- 文本不得在拖动时被意外选中，拖动中的座位应有明显视觉反馈。

### 4.4 代码边界

座位交换数据规则从页面事件中分离为可测试函数：

- 输入：当前网格、源 key、目标 key；
- 输出：移动结果、是否为空座移动、拒绝原因；
- Vue 页面负责指针状态、视觉高亮和提示；
- 保存仍通过现有 `/api/seats` 接口完成。

这样可以直接测试交换、空座移动、锁定拒绝和相同座位无操作，而无需伪造浏览器拖放对象。

### 5.1 差异分类

发现差异后按以下顺序处理：

1. 业务代码问题：修复共享 Vue 或后端代码。
2. 运行环境问题：修复 `runtimeConfig` 或 `desktopApi`。
3. 浏览器能力差异：改用跨环境标准能力或小型适配接口。
4. Windows 系统限制：保留相同业务流程，并提供明确提示和可操作替代方案。

不得通过复制一个 Desktop 专用页面来绕过差异。

## 6. 版本统一规则

### 6.1 唯一版本源

`package.json.version` 是唯一人工维护的产品版本。本轮更新为 `0.2.0`。

以下位置必须由它派生或在构建前与它严格一致：

- `src-tauri/tauri.conf.json`；
- `src-tauri/Cargo.toml`；
- Rust `DesktopBootstrap.appVersion`；
- Web/EXE 应用内版本展示；
- 更新日志的当前版本；
- portable ZIP 文件名；
- ZIP 内 README 和 `manifest.json`。

数据库 `PRAGMA user_version` 和备份 JSON 格式版本是数据结构版本，不等同于产品版本，继续独立管理并明确命名。

### 6.2 构建门禁

新增版本检查脚本，在测试和 Tauri 构建前执行：

- 读取 `package.json.version`；
- 对比 Tauri 和 Cargo 版本；
- 检查当前更新日志存在对应版本；
- 不一致时以非零状态退出并指出具体文件；
- 打包脚本继续只从 `package.json` 生成 ZIP、README 和 manifest 版本。

版本同步应由明确脚本完成，禁止在普通业务构建过程中静默修改源码。

## 7. 测试策略

### 7.1 自动测试

- 为座位移动领域函数增加测试：空座移动、两人交换、锁定源、锁定目标、无效 key、相同 key。
- 为 Pointer 状态控制增加可测试边界，验证阈值、取消和清理。
- 为版本一致性脚本增加成功和不一致失败用例。
- 保留现有 API token、CORS、路径安全、数据库迁移备份和学生班级门禁测试。
- 对功能扫描发现的高风险差异补充行为测试，不使用简单源码字符串匹配代替真实行为。

### 7.2 Web 验收

- 关闭 Tauri，仅使用普通浏览器运行 Web 原型。
- 按验收矩阵检查核心流程。
- 确认 Pointer 拖动和点击移动均可用。
- 确认版本显示为 `0.2.0`。

### 7.3 Release EXE 验收

- 关闭 Web 开发服务器。
- 从最终 ZIP 解压到中文且带空格的独立目录。
- 使用空 `data` 完成首次启动和核心流程抽样。
- 使用包含已有数据的 `data` 验证兼容启动、保存后重启和目录整体移动。
- 重点执行座位拖动交换、点击移动、保存、关闭重启后位置保持。
- 确认内置后端在正常退出后停止。

## 8. 实施顺序

1. 建立版本唯一来源和一致性构建门禁，升级至 `0.2.0`。
2. 抽离座位移动领域逻辑并用测试固定现有正确行为。
3. 用 Pointer Events 替换 HTML5 拖放事件。
4. 建立功能对照矩阵文档并逐模块扫描 Web/EXE 风险点。
5. 修复扫描发现的共享业务问题和运行时适配问题。
6. 完成 Web 自动/人工验证。
7. 重新构建 Tauri Release、生成 portable ZIP 并完成 EXE 人工 QA。
8. 将经过验证的统一代码合入 `master`，使 Web 与 EXE 从同一提交构建。

## 10. 非目标

- 不建立第二套 Desktop 专用 Vue 页面。
- 不重写现有 UI 视觉系统。
- 不在本轮引入在线升级器。
- 不把产品版本与数据库结构版本混为一体。
- 不删除、覆盖或迁移用户正式数据，除非对应数据库迁移已经具备备份和测试。
