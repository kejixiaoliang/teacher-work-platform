# 教师工作台 v0.8.0 客户端迁移小程序全过程复盘与后续方法论

> 复盘日期：2026-08-28  
> 复盘对象：`codex/v0.8.0-cloudbase-foundation` 迁移分支  
> 文档类型：项目复盘与方法论  
> 分支结论：仅作历史归档和资产来源，禁止合并到 `main`

## 1. 执行结论

本次工作没有达到“客户端功能在小程序中可用且等价”的目标。分支中有一部分数据基础设施和安全规则值得保留，但当前小程序页面和真实运行链路不能作为生产实现继续堆叠。

最重要的结论不是“以后少写一点页面”，而是：

> 跨端迁移必须先验证运行时和最小业务闭环，再扩大功能范围；自动化测试通过不能替代目标平台的真实可用性验收。

## 2. 原始目标与实际结果

### 2.1 原始目标

- 让客户端已有功能在微信小程序中可用。
- 让客户端、小程序和 CloudBase 使用同一套业务数据。
- 保持旧版本客户端数据可以被新版本导入。
- 使用微信原生身份，不额外设计账号密码登录。
- 在移动端重新组织布局，但不删减核心业务能力。

### 2.2 实际结果

已形成或部分形成：

- JSON v1 交换格式、稳定 UUID、历史字段迁移和所有权隔离规则。
- CloudBase 集合、索引、权限和一组带认证边界的云函数。
- 学生/成绩 Excel 交换、完整敏感数据备份导出和导入预检逻辑。
- 客户端与小程序的功能映射、UI 规划和大量自动化契约测试。

没有完成或没有被真实证明：

- 小程序首屏和各页面在微信开发者工具中的稳定编译、启动和点击操作。
- 小程序与客户端的完整功能等价。
- 小程序真实身份下的读写、文件选择、备份和恢复闭环。
- 真正的双向同步、冲突处理和离线恢复。

## 3. 本次过程中的关键偏差

### 3.1 把“文件齐全”误认为“产品可用”

页面、JSON、WXSS、JS 文件都存在，只能证明工程结构完整，不能证明页面已经注册、编译、渲染、可导航和可操作。页面完整性测试在早期给了过强的完成感。

### 3.2 在运行时基线未稳定前扩大范围

还没有完成最小的“微信身份 → 数据集 → 班级 → 学生列表”闭环，就继续加入座位、成绩、考勤、请假、值日、备份、Excel 和多套 UI。任何底层入口问题都会被放大到几十个页面。

### 3.3 把桌面端逻辑直接搬进小程序页面

客户端和小程序虽然共享业务模型，但运行时、文件 API、导航、生命周期、错误处理和交互密度不同。共享规则是正确方向，直接共享页面组织方式却造成了耦合和体验问题。

### 3.4 真实开发者工具验收被推迟

稳定版开发者工具窗口、worktree 路径、缓存和用户屏幕占用没有在每个节点固定核验。最后出现了旧日志、旧目录和当前源码混淆的问题。没有真实点击证据时，不应把页面称为“完成”。

### 3.5 源文件污染暴露了编辑流程缺口

补丁标记文本曾被写入 `identity/index.wxss`，触发 `unexpected '\\'` 和伪类解析错误。这不是业务逻辑问题，而是提交前没有做源码污染扫描，也没有对目标平台编译一次。

### 3.6 测试边界表达不够诚实

大量测试验证了函数契约、字符串和页面入口，但没有覆盖微信 WXSS 编译器、页面生命周期、真实 CloudBase 身份、文件系统和真机布局。测试数量很大，却没有准确表达“哪些已经在目标平台验证”。

### 3.7 配置和部署状态没有成为显式前置条件

`env.js` 被忽略且依赖本地存在；CloudBase 云函数管理端冒烟没有微信 `OPENID`，只能证明认证拦截生效，不能证明真实业务成功。配置缺失时必须显式阻止业务操作，而不是让页面看起来像可以使用。

## 4. 真正值得保留的成果

### 4.1 数据兼容模型

- 新客户端必须导入旧客户端已承诺支持的 JSON、ZIP 和数据库数据。
- 软件版本、数据库版本、JSON `formatVersion` 和 ZIP 版本独立维护。
- UUID、父子关系、字段迁移和缺失字段默认值有明确规则。
- 历史格式通过迁移器进入统一内部模型，不直接映射数据库。

### 4.2 数据安全边界

- 所有者身份从微信或服务端上下文取得，不能信任客户端传入的 `ownerId`。
- 查询和写入同时限制 `ownerId`、`datasetId`、`classUuid`。
- 导入采用预检、预览、提交三阶段。
- 重复导入使用 `exportId` 等来源标识做幂等保护。
- 默认软删除、修订号和恢复前快照规则清晰。
- 密码摘要、Token、恢复密钥和本地绝对路径不进入备份。

### 4.3 可迁移的算法和测试

学生/成绩文件解析、公式注入防护、旧字段转换、备份完整性、压缩包路径安全、请假—考勤联动和座位算法都有可复用的纯逻辑部分。它们应脱离当前页面重新测试，而不是原样搬运。

## 5. 以后必须采用的工程流程

### 阶段 A：先固定边界

在写代码前写清楚：目标客户端、非目标平台、数据契约、身份方式、首个闭环和不可触碰的数据。小程序不是本分支的默认生产目标，任何跨端工作都必须先说明验收平台。

### 阶段 B：先做运行时冒烟

只建立三个页面：启动页、身份/环境页、班级列表页。先在目标工具和至少一个真实设备尺寸下确认：

- 项目根目录正确。
- JS、WXML、WXSS 都能编译。
- 页面能启动和切换。
- 未配置环境时有明确错误。
- 使用脱敏数据能完成一次真实读取。

### 阶段 C：只做一条纵向闭环

推荐顺序：

```text
微信身份
  → 数据集选择
  → 班级选择
  → 学生列表
  → 学生详情
  → 新增/编辑/软删除
  → 客户端按同一 UUID 读取
```

这一条链在目标平台真实通过后，才允许加入第二个业务模块。

### 阶段 D：按模块逐个迁移

每个模块必须经过：

1. 对照客户端字段和行为。
2. 明确云函数输入、输出和权限边界。
3. 做页面空状态、错误状态和无权限状态。
4. 写契约和回归测试。
5. 在开发者工具中真实点击。
6. 记录证据和已知限制。

### 阶段 E：最后再做高风险能力

完整备份、Excel 文件、恢复、同步和身份绑定应在基础导航稳定后实施。每个高风险能力必须有独立的脱敏数据集、预检、确认、回滚和审计记录。

## 6. 未来验收证据分级

| 级别 | 证据 | 可以说什么 |
| --- | --- | --- |
| L0 | 文件存在、静态检查通过 | 工程文件已准备 |
| L1 | 单元/契约测试通过 | 逻辑契约通过 |
| L2 | 目标平台编译通过 | 目标平台可编译 |
| L3 | 模拟器点击和错误路径通过 | 页面基本可用 |
| L4 | 脱敏真实身份下读写通过 | 业务闭环可用 |
| L5 | 真机、多尺寸、恢复/回滚和历史数据通过 | 可以进入发布评估 |

没有达到 L2，不得说“可以使用”；没有达到 L4，不得说“业务闭环完成”；没有达到 L5，不得说“生产可发布”。

## 7. 数据兼容长期规则

- 新客户端和未来新小程序都必须导入旧版本已承诺的数据。
- 新版本只导出最新格式，旧格式迁移器永久保留。
- 历史数据库迁移脚本不可修改，只能追加。
- 每个发布版本保存脱敏旧数据样本。
- 每次格式变化必须先更新迁移器、测试样本和回滚说明。
- 小程序不能为了页面方便创建另一套 ID、字段或状态。
- 任何跨端实现都不能削弱客户端原有的旧数据导入能力。

## 8. 分支和资产治理

- `codex/v0.8.0-cloudbase-foundation` 只作为历史实验和资产归档分支，禁止合并到 `main`。
- 新小程序应从稳定客户端分支重新创建独立分支，不以当前小程序页面为模板。
- 可提取共享契约、纯业务算法、云函数安全规则和测试；页面、样式和运行时连接必须重新设计。
- CloudBase 已部署资源不能因为放弃本分支就默认删除，必须单独盘点、停用或保留，并确认是否还有其他客户端依赖。
- 归档文档必须标注“设计目标”“代码已实现”“目标平台已验证”三种状态，避免历史记录被误读为发布承诺。

## 9. 最终反思

这次失败不是因为客户端数据模型不值得做，也不是因为小程序天然不适合这个产品；失败在于把一个需要多轮真实验证的迁移项目，按“先铺满功能、最后统一验收”的方式推进了。

今后最重要的改变是降低一次性范围、提高每一步的证据强度：先让一个人可以在目标设备上完成一件真实工作，再扩展下一件；先证明数据不会丢，再讨论页面是否漂亮；先承认未验证，再决定是否继续投入。
