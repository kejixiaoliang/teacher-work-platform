# 教师工作台 v0.9.0 自动更新分支完整总结与复盘

## 一句话结论

v0.9.0 完成了从绿色便携版到 Windows 当前用户安装版和 Tauri 自动更新的升级。安装版经过本机和另一台 Windows 电脑的真实验收，安装、启动、检查更新、自动更新、重启和数据恢复链路均已验证。最终稳定资产已经发布到 CloudBase `stable` 目录。

本版本没有购买 Windows Authenticode 证书，这是一次明确的发布决策。安装包仍然使用 Tauri updater 签名和 `.sig` 文件进行更新包完整性验证，但部分 Windows 电脑可能显示“未知发布者”或 SmartScreen 提示。

## 1. 分支和发布范围

工作从主分支建立独立 worktree 和分支开始，避免直接污染主分支。

```text
分支：codex/v0.9.0-auto-update
Worktree：E:\CodeFile\MyAIProject\Reasonix-test\teacher-work\.worktrees\v0.9.0-auto-update
版本：0.9.0
目标平台：Windows x64
安装形式：当前用户 NSIS 安装版
数据目录：%LOCALAPPDATA%\TeacherWork\data
更新服务：CloudBase 静态托管
```

便携版继续保留原有行为。便携版使用 EXE 同级的 `data`、`backups` 和 `logs`，不接入可执行自动更新。

## 2. 完成的功能和基础建设

### 2.1 版本契约

package、Cargo、Tauri 配置和前端版本记录统一为 `0.9.0`。增加了版本契约检查，构建前会阻止版本号不一致。

### 2.2 安装版运行目录

安装版和便携版采用独立运行 profile。安装版把程序安装到当前用户目录，把数据库、附件、备份和日志放到 `%LOCALAPPDATA%\TeacherWork`。Node sidecar 只通过 `TEACHER_WORK_DATA_DIR` 接收数据目录，业务代码不再自行判断运行形式。

### 2.3 安装包资源

安装版构建时显式准备并映射以下资源。

```text
resources\runtime\node.exe
resources\app\server\index.js
resources\app\node_modules\...
```

这解决了最初安装后程序找不到内置 Node 运行时和后端入口的问题。

### 2.4 Tauri updater

安装版接入 Tauri updater，便携版和普通浏览器环境不执行自动安装。更新界面包含当前版本、数据库版本、更新说明、检查状态、下载进度、失败提示和安装前确认。安装前会创建带附件的恢复点，并在更新过程中退出应用、停止后台服务、安装更新和重启。

### 2.5 关闭生命周期和进程保护

桌面层将窗口关闭、Tauri 退出事件和 Node sidecar 回收收口为幂等流程。退出时会取出唯一的子进程，执行终止并等待，不使用窗口回调中的 `std::process::exit(0)`。

安装版增加了单实例互斥、Windows Job Object 后台进程托管、关闭应用树后再复制安装文件、当前安装目录精确匹配 `node.exe`、NSIS 安装前和卸载前清理 hook，以及不删除用户数据目录等保护。

## 3. 实际遇到的问题和处理过程

### 3.1 便携版关闭后后台进程没有完全退出

表现是窗口已经关闭，但 Node sidecar 仍可能存在，导致端口、SQLite 或文件句柄继续占用。

根因是关闭流程分散在窗口回调、退出事件和子进程管理中，某些路径只返回成功，没有完成子进程的终止和等待。

处理方式是建立退出契约测试，统一使用 `Mutex<Option<Child>>` 管理 sidecar，退出时 `take()`、`kill()`、`wait()`，并让多个退出事件可以安全重复执行。

### 3.2 首次安装后点击桌面图标闪退

最初安装包虽然包含后端文件，但资源没有按照程序实际查找的 `resources\runtime` 和 `resources\app` 目录落地。后续又发现测试使用的 HTTP updater endpoint 会让 updater 插件在 Tauri setup 阶段拒绝初始化。

处理方式是构建入口预置 Node、server 和生产依赖，安装版将运行时目录整体映射到 `resources\`，构建入口强制要求 updater endpoint 使用 HTTPS，再用真实安装包重新安装，确认 Node、server、SQLite 依赖和数据库迁移均可用。

这次故障说明，桌面应用不能只验证源码构建成功，必须用最终安装器验证实际落地目录和真实启动过程。

### 3.3 更新页出现 Vue Proxy 的 `Symbol(nativeUpdate)` 错误

表现是可以发现 v0.9.1，但点击“备份并更新”时出现原生 updater 对象被 Vue Proxy 深层代理的不变量错误。

根因是 Tauri native updater 返回对象包含不可配置的原生属性，被 Vue 深层响应式代理包装后触发了 JavaScript Proxy 不变量错误。

处理方式是用 `shallowRef` 保存 native updater 结果，只对界面需要的普通字段做归一化，不让 Vue 深层代理原生对象。随后补充 updater contract 测试和更新页面回归测试。

经验是，原生插件对象、DOM 对象、浏览器原生对象和带 Symbol 的对象不应直接放入 Vue 深层响应式状态。

### 3.4 更新安装时 `better_sqlite3.node` 和 `node.exe` 写入失败

表现是 NSIS 安装过程中出现以下文件无法写入的提示。

```text
resources\app\node_modules\better-sqlite3\build\Release\better_sqlite3.node
resources\runtime\node.exe
```

实际原因是多个生命周期问题叠加，包括应用或 sidecar 仍在运行、updater 重启和 NSIS 安装器重复 relaunch、安装前只停止了部分进程，以及 NSIS hook 中 PowerShell 的 `$` 变量没有正确转义。

最终处理链路是更新器只负责触发安装，安装前显式停止 Node 后台服务并等待，NSIS hook 关闭当前应用树，只按当前安装目录精确匹配对应 `node.exe`，并修正 `$$root`、`$$node`、`$$_.Name` 等 PowerShell 变量转义。

本机最后一次测试还出现过文件占用提示，但点击“中止”取消后重新启动安装器即可顺利完成。这说明旧安装进程或残留句柄已被解除，但正式验收规则仍然是不允许用“忽略”掩盖错误。

### 3.5 CloudBase 下载链接返回 `INVALID_REQUEST`

云端对象实际已经存在，问题来自之前手工提供的中文文件名 URL 编码错误。CloudBase 返回了 `INVALID_REQUEST`，官方错误码页面只是该错误的说明入口。

处理方式是重新上传纯英文文件名副本，并把外部测试文档改为优先使用 ASCII 文件名链接。以后自动生成的 `latest.json` 仍由脚本负责对中文文件名执行 `encodeURIComponent`，不再手工拼接编码后的 URL。

### 3.6 VPN 开关影响检查更新

测试中出现过关闭 VPN 无法检查更新、开启 VPN 可以检查的情况，之后又恢复为两种状态都可以打开和使用。

这更符合本机代理、DNS、路由或 VPN 分流策略影响 HTTPS 访问的表现，不足以证明 CloudBase 对国内用户不可用。外部 Windows 电脑已在无此问题的情况下完成安装和更新验收。

应用本身保留网络失败的可理解提示。后续若再次出现，先记录 VPN 状态、Windows 系统代理、DNS 和目标 URL，再区分客户端网络问题与托管服务问题。

### 3.7 没有购买 Authenticode 证书

Tauri updater 签名和 Windows Authenticode 是两件事。Tauri updater 签名用于客户端验证更新包内容，v0.9.0 已具备并通过测试。Authenticode 用于让 Windows 更容易识别发布者，减少 SmartScreen 或未知发布者提示。

经过讨论，本版本明确不购买 Authenticode 证书，面向几十到几百位用户发布。该决定已经写入发布清单和长期 SOP，后续不能把 v0.9.0 描述为“已完成 Windows 代码签名”。

## 7. 经验教训

### 安装包必须做真实安装验收

源码测试只能证明逻辑，不能证明资源目录、NSIS 行为、Windows 文件锁、WebView2 启动和桌面快捷方式都正确。以后安装版改动必须生成最终安装器，在真实 Windows 环境走完整流程。

### 失败提示不能被“忽略”掩盖

安装器显示文件写入失败时，选择“忽略”只能让安装流程继续，不能证明文件已经正确落地。发布验收遇到这类错误必须中止、记录和重新定位。

### 发布地址和资产路径必须可重复

版本资产使用不可变目录，`latest.json` 最后上传。中文文件名由脚本编码，外部分享优先使用 ASCII 文件名，避免聊天工具和浏览器改写 URL。

### 更新器只做更新，应用负责数据安全

更新器负责检查、验签、下载、安装和重启。数据库快照、附件备份、迁移失败恢复和用户确认由应用负责。

### 本机网络现象要和服务故障分开

VPN、系统代理和 DNS 会改变访问路径。检查更新失败时要记录本机网络条件，不能只根据一台电脑的 VPN 开关下结论。

## 8. 当前已知限制

- v0.9.0 只给安装版提供自动更新，便携版仍需手动替换。
- Windows Authenticode 未签名，部分用户可能看到系统信任提示。
- CloudBase 测试目录仍保留测试资产，正式目录与测试目录必须继续分开。
- 未来版本不能原地覆盖已发布的 `stable/v0.9.0/` 文件，应创建新的不可变版本目录。
- 如果未来需要更高的 Windows 信任度，再单独评估 Authenticode、Microsoft Store 或托管签名服务。

## 9. 结论

本次分支完成了 v0.9.0 的主要目标，并把一次真实发布中遇到的安装、进程、原生对象、网络和云端路径问题沉淀成了可复用规则。v0.9.0 可以作为当前稳定安装版向用户发放。后续新版本应直接遵循配套的《教师工作台自动更新发布 SOP》，不再从零回忆目录、密钥、清单和验收顺序。
