# 教师工作台绿色便携版发布、升级与数据库迁移注意事项

> 文档状态：当前发布与升级参考资料。

## 1. 文档目的

本文记录“教师工作台”从 Web 形态开发、验证，到封装为 Tauri 绿色便携版时需要长期遵守的设计原则。

当前项目已经具备完整的三层结构：

- 前端：Vue 3 + Vite；
- 后端：Node.js + Express；
- 数据库：SQLite（`better-sqlite3`）；
- 文件数据：项目 `data/files/` 目录；
- 前后端通信：REST API。

现阶段计划优先发布可手动升级的绿色便携版，暂不实现在线自动升级。但第一版仍应提前划清程序与数据的边界，避免未来增加在线升级、数据库迁移和回滚能力时被迫重构。

---

## 2. 总体开发路线

建议继续采用以下开发方式：

1. 先以完整 Web 应用形态开发前端、后端和数据库；
2. 在 Web 模式下完成业务功能和接口验证；
3. 验证生产构建结果；
4. 再同步到 Tauri 桌面壳中验证；
5. 最终以绿色便携包交付。

Web 端应长期保留，作为快速开发、调试和自动化测试入口。Tauri 主要承担桌面窗口、启动管理、本地文件能力和最终交付。

需要注意：Tauri 不能天然把现有 Express 和 `better-sqlite3` 原样变成 Rust 后端。未来需要在以下方向中选择：

- 将 Node/Express 后端作为 Sidecar 随桌面程序启动；
- 将后端和数据库访问逐步迁移为 Tauri/Rust Command；
- 保留统一的数据访问接口，分别提供 Web REST 和 Tauri 适配器。

无论最终选择哪种方式，前端页面都不应散落大量直接请求代码。建议保持统一 API/数据访问层，使页面不依赖具体运行环境。

## 3. 绿色便携版的定义

绿色版不写入系统安装目录，不要求传统安装流程。用户完成一次解压后，可以直接双击 EXE 启动，程序和数据均保存在同一个便携文件夹中。

用户不应直接在 ZIP 压缩包内部双击 EXE。Windows 可能把文件临时解压到临时目录运行，导致数据库和上传文件保存位置不稳定。正确流程是：

```text
下载 ZIP
→ 解压整个“教师工作台”文件夹
→ 双击启动程序
→ 数据保存在该文件夹的 data/ 中
```

建议第一版目录结构如下：

```text
教师工作台/
├─ app/                 # 程序文件，可被新版替换
│  └─ 教师工作台.exe
├─ data/                # 用户数据，升级时永不覆盖
│  ├─ teacher.db
│  └─ files/
├─ backup/              # 自动和手动备份
├─ logs/                # 启动、迁移和升级日志
├─ 启动教师工作台.exe   # 可选：稳定的启动器
└─ 使用说明.txt
```

核心边界：

```text
app/     可以替换
data/    永远保留
backup/  永远保留
logs/    可以按保留策略清理
```

绿色版目录必须位于用户可写的位置，例如桌面、文档目录或其他数据盘。不建议放入 `C:\Program Files` 等通常需要管理员权限的目录。

程序启动时应检查所在目录是否可写。如果目录只读、位于压缩包临时目录或没有足够空间，应停止数据写入并向用户给出清晰提示。

## 4. 第一版：手动绿色升级

第一版暂不实现在线更新。推荐发布一个不包含真实用户数据的新版 ZIP，并提供以下升级流程：

```text
1. 关闭旧版教师工作台；
2. 备份旧版 data/；
3. 解压新版程序；
4. 只替换 app/ 中的程序文件；
5. 保留原 data/ 和 backup/；
6. 启动新版，自动执行必要的数据库迁移。
```

更新包不得包含可能覆盖用户数据的 `data/teacher.db`。如果必须附带空目录，应确保解压工具不会用空目录或示例数据库覆盖现有内容。

第一版建议至少提供以下应用内能力：

- 显示应用版本和数据库版本；
- 打开数据目录；
- 完整备份；
- 从完整备份恢复；
- 数据库迁移前自动备份；
- 导出诊断日志；
- 清晰的升级说明。

## 5. 第二版：内置升级助手的原理

Windows 正在运行的 EXE 通常不能直接覆盖自身，因此在线升级一般分为主程序和独立更新进程。

```text
主程序检查版本
→ 下载更新包到临时目录
→ 校验完整性和数字签名
→ 创建恢复点
→ 启动独立更新助手
→ 主程序退出
→ 更新助手替换或切换程序版本
→ 重新启动新版
→ 执行健康检查
→ 成功则清理临时文件
→ 失败则恢复旧程序和旧数据库
```

### 5.1 在线升级所需组件

未来实现在线升级时，至少需要：

- 规范的语义化版本号，例如 `1.2.0`；
- HTTPS 更新地址；
- 静态版本 JSON 或动态更新服务；
- 对应系统和架构的程序更新包；
- SHA-256 等完整性摘要；
- 更新包数字签名；
- 安全保存的签名私钥；
- 内置于应用的验证公钥；
- 下载进度、取消、超时和失败重试；
- 临时下载及解压目录；
- 独立启动器或更新助手；
- 新版启动健康检查；
- 程序和数据库联合回滚；
- 发布日志与升级日志。

一个简单的静态版本文件可以包含：

```json
{
  "version": "1.2.0",
  "notes": "新增成绩导入并修复座位表打印问题",
  "publishedAt": "2026-08-04T10:00:00+08:00",
  "url": "https://example.com/releases/teacher-work-1.2.0.zip",
  "sha256": "更新包摘要",
  "signature": "更新包数字签名"
}
```

### 5.2 签名与安全

SHA-256 只能确认文件是否损坏或发生变化，不能单独证明更新包由项目发布者提供。数字签名用于验证发布者身份：

- 私钥只用于构建和签署更新包，不得放进代码库或交付包；
- 公钥可以内置在客户端，用来验证更新包；
- 私钥必须安全备份；
- 私钥丢失后，已发布客户端可能无法信任后续更新；
- 私钥泄露后，攻击者可能伪造更新包，应预先规划密钥轮换机制。

更新包签名和 Windows 代码签名不是同一件事：前者供应用验证更新包，后者供 Windows 验证 EXE 发布者。更新包签名属于必要能力，Windows 代码签名在扩大分发范围时建议配置。

### 5.3 绿色版推荐的版本目录方案

与直接覆盖正在使用的 EXE 相比，下载到独立版本目录再切换会更可靠：

```text
教师工作台/
├─ launcher.exe
├─ current.json
├─ versions/
│  ├─ 1.1.0/
│  │  └─ 教师工作台.exe
│  └─ 1.2.0/
│     └─ 教师工作台.exe
├─ data/
├─ backup/
└─ logs/
```

更新步骤：

```text
下载 1.2.0
→ 解压到 versions/1.2.0
→ 校验全部文件
→ 将 current.json 从 1.1.0 切换为 1.2.0
→ 启动新版
```

如果新版启动失败，可以把 `current.json` 切回 `1.1.0`。启动器应尽量小且稳定，降低启动器自身升级的频率。

Tauri 官方更新器在 Windows 上主要围绕 MSI/NSIS 安装产物设计。标准安装版可以优先采用官方更新器；真正的绿色便携版更适合保留 Tauri 的版本检查和签名思路，并实现自己的版本目录、启动器和回滚流程。

## 6. 数据库演进原则

数据库结构发生变化是正常的。风险不在变化本身，而在于变化是否可追踪、可测试、可恢复。

项目当前已使用 SQLite `user_version` 管理迁移，并已有 v1、v2、v3 迁移。后续应将其发展为正式、永久保留的迁移序列：

```text
用户数据库 v1
→ 执行 v2
→ 执行 v3
→ 执行 v4
→ 执行 v5
→ 达到新版要求
```

不能假设所有用户都从紧邻的上一个版本升级。长期未升级的数据库也必须能够逐版本迁移到最新版。

建议后续将数据库代码逐步拆分为：

```text
server/db/
├─ index.js
├─ schema.js
└─ migrations/
   ├─ 001-initial.js
   ├─ 002-student-follow-up.js
   ├─ 003-metric-source.js
   ├─ 004-xxx.js
   └─ 005-xxx.js
```

### 6.1 迁移的基本规则

1. 每次数据库结构或重要数据语义变化都必须增加新版本；
2. 已经发布的迁移脚本不可修改，只能追加新迁移；
3. 不得只修改初始建表代码而忽略旧数据库；
4. 每条迁移都必须能够在真实旧版本数据库副本上测试；
5. 新版程序不得无提示地打开比自己更新的数据库；
6. 数据库版本与最低可运行程序版本应有明确对应关系；
7. 迁移失败时禁止带着半迁移状态继续运行；
8. 日志应记录迁移前版本、目标版本、执行结果和错误原因。

### 6.2 新增字段

新增字段通常风险较低，但应尽量：

- 允许为空；或
- 提供明确默认值；
- 说明旧记录如何补全；
- 为新增约束编写数据检查。

### 6.3 修改字段或业务含义

字段重命名、数据编码变化和业务语义变化必须提供明确的旧值到新值转换规则，并检查异常值。例如从中文枚举迁移到代码枚举时，必须说明空值和未知值如何处理。

### 6.4 删除字段

删除字段属于高风险操作。优先采用分阶段停用：

```text
第一阶段：新版停止写入旧字段；
第二阶段：保留旧字段若干版本，观察兼容性；
第三阶段：确认无需回滚后，再物理删除。
```

SQLite 的复杂字段变更可能需要建立新表、复制转换数据、校验记录数、替换旧表并重建索引与外键。没有充分收益时，保留一个已停用字段通常比立即删除更安全。

## 7. 数据库迁移与备份流程

推荐迁移流程：

```text
检查数据库完整性
→ 检查目标目录可写和磁盘空间
→ 创建升级前备份
→ 开启数据库事务
→ 按顺序执行所有缺失迁移
→ 验证表、字段、索引、外键和关键记录
→ 更新数据库版本
→ 提交事务
→ 启动新版业务
```

任何一步失败时：

```text
回滚事务
→ 保留原数据库
→ 记录错误日志
→ 停止进入新版业务
→ 引导用户恢复备份或继续使用旧版
```

备份目录建议包含：

```text
backup/
└─ 2026-08-04_153000-v1.2.0-to-v1.3.0/
   ├─ teacher.db
   ├─ files/             # 涉及文件变更时必须包含
   └─ backup.json
```

`backup.json` 至少记录：

```json
{
  "appVersion": "1.2.0",
  "databaseVersion": 3,
  "targetAppVersion": "1.3.0",
  "targetDatabaseVersion": 4,
  "createdAt": "2026-08-04T15:30:00+08:00"
}
```

## 8. 程序回滚必须与数据库回滚配套

只回滚程序、不回滚数据库可能导致旧程序无法识别新数据库。例如：

```text
程序 1.2.0 → 数据库 v3
程序 1.3.0 → 数据库 v4
```

如果用户已升级到程序 1.3.0 和数据库 v4，仅把程序切回 1.2.0 可能无法正常运行。因此每次升级都应创建联合恢复点：

```text
恢复点
├─ 程序版本：1.2.0
├─ 数据库版本：v3
├─ 数据库备份：teacher.db
└─ 文件数据快照：按迁移风险决定是否包含
```

发生故障时，程序版本和数据库版本应一起恢复。

数据库迁移设计还应尽量保证小版本间向后兼容。破坏性迁移必须创建完整备份，并明确旧程序能否继续打开迁移后的数据库。

## 9. 数据库之外的文件数据

当前项目还包含 `data/files/`。涉及文档文件名、目录结构、文件归属或数据库文件路径字段的迁移时，仅备份 SQLite 数据库并不充分。

应遵守：

- 普通字段迁移至少备份 `teacher.db`；
- 涉及文件移动、重命名或删除时，备份完整 `data/`；
- 文件迁移采用“先复制、校验成功、再删除旧文件”；
- 数据库记录和实际文件必须在同一迁移流程中验证；
- 迁移中断后能够判断哪些文件已经处理，避免重复操作；
- 不得因为数据库回滚而误删用户新增的文件。

## 10. 发布前升级测试矩阵

正式发布前不能只测试全新数据库。至少应验证：

```text
全新安装              → 建立最新数据库
旧 v1 数据库          → 升级到最新版
旧 v2 数据库          → 升级到最新版
旧 v3 数据库          → 升级到最新版
无网络                → 不影响离线使用
下载中断              → 旧版仍可启动
更新包损坏            → 拒绝安装
更新包签名不正确      → 拒绝安装
磁盘空间不足          → 不开始替换和迁移
程序目录只读          → 明确提示并停止写入
数据库迁移失败        → 原数据库可恢复
新版启动失败          → 程序和数据库联合回滚
跨多个版本升级        → 迁移按顺序完整执行
包含大量上传文件      → 数据和文件保持一致
```

每个正式版本应保留若干经过脱敏的旧版本数据库样本，用于持续回归测试。

## 11. 分阶段实施建议

### 阶段一：当前开发阶段

- 继续以 Web 模式开发和验证；
- 保留项目下的 `data/`；
- 明确当前数据库结构的基线版本；
- 开始规范化迁移脚本；
- 区分程序文件与用户数据；
- 不急于实现在线升级。

### 阶段二：第一版绿色便携包

- 固定绿色版目录结构；
- 手动替换 `app/`，永不覆盖 `data/`；
- 提供打开数据目录、完整备份和恢复；
- 数据库迁移前自动备份；
- 检查目录可写性；
- 提供明确升级说明；
- 完成旧数据库升级测试。

### 阶段三：完善手动升级体验

- 提供离线更新包导入；
- 自动检查更新包版本、摘要和签名；
- 创建程序与数据库联合恢复点；
- 自动执行替换并支持失败回滚；
- 用户仍可在无网络环境下升级。

### 阶段四：在线升级助手

- 增加线上版本信息和更新包托管；
- 增加在线检查、下载进度和失败重试；
- 使用数字签名验证更新；
- 采用版本目录切换；
- 增加新版健康检查和自动回滚；
- 根据用户规模考虑 Windows 代码签名和更新渠道。

## 12. 第一版发布前必须确定的决策

在正式交付第一版前，需要明确：

1. 首个承诺长期保留用户数据的正式版本号；
2. 当前数据库基线版本；
3. 绿色版最终目录结构；
4. 数据库和上传文件的备份格式；
5. 手动升级时允许替换和禁止替换的目录；
6. 旧程序遇到更高数据库版本时的处理方式；
7. 数据库迁移失败时的用户提示和恢复入口；
8. 备份保留数量和清理策略；
9. 是否同时提供完整便携包和纯程序更新包；
10. 未来优先采用 Node Sidecar 还是 Rust/Tauri 数据层。

## 13. 核心结论

绿色便携版适合本项目，便于用户理解、备份和迁移。它并不会天然导致升级困难，前提是从第一版开始遵守四项原则：

1. **程序可替换**：程序文件与用户数据严格分离；
2. **数据不覆盖**：任何更新包都不能覆盖真实 `data/`；
3. **迁移可追踪**：数据库变化只能通过有版本、不可篡改的迁移脚本完成；
4. **失败可恢复**：程序升级、数据库迁移和文件迁移都必须有备份与回滚路径。

第一版可以只提供手动绿色升级，但目录、迁移和备份设计应为未来的离线升级助手与在线升级助手预留清晰边界。
