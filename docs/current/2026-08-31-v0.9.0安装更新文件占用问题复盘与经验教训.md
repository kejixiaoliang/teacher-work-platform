# 教师工作台 v0.9.0 安装更新文件占用问题复盘与经验教训

## 1. 复盘结论

本次安装和自动更新问题最终已经解决，并完成本机实测：

- 0.9.0 安装包可以正常安装；
- 安装后桌面图标可以正常启动，不再闪退；
- 0.9.0 检查更新可以发现 0.9.1；
- 0.9.0 → 0.9.1 自动更新可以完成，安装过程中不再出现文件写入错误；
- 更新前会创建包含附件的本地恢复点；
- v0.8 导出的备份仍然可以恢复使用。

最终验收包：

```text
E:\工作台测试\教师工作台_0.9.0_进程保护三次修复-setup.exe
```

本次复盘的核心结论是：Windows 自动更新不是单一的“下载并覆盖文件”动作，而是“前端确认、数据备份、后台服务关闭、进程回收、NSIS 安装器、构建配置合并、签名资产和真实安装验收”共同组成的链路。任何一层没有验证，源码测试通过也不能代表用户安装一定成功。

## 2. 用户看到的两个主要问题

### 2.1 安装后点击图标立即闪退

安装器表面上显示成功，但桌面图标启动后窗口瞬间消失。根因不是前端页面，而是安装版没有完整准备内置 Node 运行时和后端资源，主程序无法启动本地 server。

安装版实际需要的资源布局是：

```text
安装目录\resources\runtime\node.exe
安装目录\resources\app\server\index.js
```

### 2.2 安装或自动更新时无法写入文件

NSIS 报错集中在：

```text
resources\app\node_modules\better-sqlite3\build\Release\better_sqlite3.node
resources\runtime\node.exe
```

这不是 `better-sqlite3` 损坏，也不是安装包缺文件，而是旧版内置 Node 进程仍然运行并持有这些文件的 Windows 文件锁。

## 3. 逐轮排查与修复过程

### 3.1 先修复运行时资源布局

构建流程增加运行时准备脚本，把 Node、server 和生产依赖按安装版的实际路径放入 Tauri resources。这样解决了安装后无法启动的问题，但没有解决更新期间的后台进程残留。

### 3.2 第一轮生命周期修复

增加了：

- 更新前显式停止后台服务并等待退出；
- 安装版单实例互斥体；
- Windows Job Object 托管内置 Node；
- 主程序关闭时回收 sidecar；
- 启动时按完整路径清理同一安装目录的残留 Node；
- NSIS 安装前关闭主程序进程树。

这说明仅修复应用内部的关闭生命周期还不够，因为安装器运行在应用进程之外，必须在安装器边界再次处理残留进程。

### 3.3 第二轮发现构建配置合并问题

安装版构建使用基础 Tauri 配置和动态生成的 updater 配置叠加。第一次检查源码配置时，`installerHooks` 看起来存在；但生成的 updater overlay 没有显式携带该字段，最终 NSIS 安装器可能没有得到清理 hook。

修复方式：

- 在 `scripts/build-tauri.mjs` 生成 overlay 时显式写入 `bundle.windows.nsis.installerHooks`；
- 检查生成后的 `tauri.updater.conf.json`；
- 检查最终生成的 `installer.nsi` 是否包含 `hooks.nsh` 的 `!include` 以及 pre-install/pre-uninstall 调用。

### 3.4 实机复现并定位最后一个根因

用户再次运行二次修复包时，安装器仍然报告文件无法写入。对本机进程进行精确查询后发现：

```text
PID 14124
C:\Users\kangt\AppData\Local\教师工作台\resources\runtime\node.exe
父进程已不存在
```

手动结束这个精确路径匹配的孤儿进程后，取消原安装并重新运行同一个安装包，安装立即成功。这一步把“文件锁”从推测变成了已验证事实，也证明之前的 NSIS 清理命令没有真正完成清理。

### 3.5 最终定位 NSIS 与 PowerShell 的变量转义边界

NSIS 和 PowerShell 都使用 `$` 作为变量前缀。NSIS 脚本中的 PowerShell 变量如果直接写成 `$root`、`$node`、`$_`，会先被 NSIS 解析，传给 PowerShell 的命令就可能失真。

最终修复将其写成：

```text
$$root
$$node
$$_.Name
$$_.ExecutablePath
$$_.ProcessId
```

同时保留：

- `$INSTDIR` 和 `$SYSDIR` 作为 NSIS 变量正常展开；
- 只匹配当前 `$INSTDIR\resources\runtime\node.exe`；
- 结束进程后等待其退出；
- 同时覆盖 `NSIS_HOOK_PREINSTALL` 和 `NSIS_HOOK_PREUNINSTALL`。

## 4. 哪些尝试没有解决问题，以及原因

### 4.1 只在应用内部调用 shutdown

应用内部的 `kill + wait` 可以处理正常退出，但无法覆盖：

- 应用异常退出；
- 更新器和旧应用短暂重叠；
- sidecar 脱离父进程继续运行；
- 用户直接再次运行安装包。

因此必须同时有应用生命周期保护和安装器前置清理。

### 4.2 只检查源码配置

源码中的配置正确，不代表动态合并后的最终配置正确。以后必须检查构建产物中的 overlay 和最终 `installer.nsi`，不能只看 `tauri.installed.conf.json`。

### 4.3 只检查“是否包含清理代码”

测试曾经检查了 `Stop-Process`、`Wait-Process` 和路径匹配，但没有检查 NSIS 对 PowerShell `$` 的转义。代码文本看起来完整，实际脚本执行语义却不完整。

以后遇到多层脚本嵌套，测试必须覆盖“传入层”和“执行层”的语法边界。

### 4.4 点击“忽略”继续安装

“忽略”只是跳过当前被锁定的文件，可能形成新旧文件混合的半更新状态。它不能作为正常安装方案，也不能作为验收通过的依据。

正确处理顺序是：

1. 点击“中止”；
2. 关闭或清理持有文件锁的本应用进程；
3. 重新运行修复后的安装包；
4. 安装结束后检查应用版本、启动和数据完整性。

## 5. 以后防止同类问题的工程规则

### 5.1 进程生命周期规则

- 所有长期运行的 sidecar 必须由主程序明确持有并管理；
- 正常退出必须执行停止并等待；
- 异常退出必须有 Job Object 或同等的进程回收机制；
- 启动时只清理当前安装目录下的同一 runtime，不得按 `node.exe` 名称全局结束其他项目。

### 5.2 安装器规则

- NSIS 覆盖安装前必须关闭主程序进程树；
- 必须精确清理当前 `$INSTDIR` 对应的残留 Node；
- 清理后必须等待文件句柄释放；
- 同时验证安装和卸载两个生命周期入口；
- 任何无法覆盖的文件都不能通过“忽略”作为验收结果。

### 5.3 构建规则

每次安装版构建至少检查：

- 版本号是否一致；
- updater endpoint 是否为 HTTPS；
- public key 是否注入；
- 私钥是否只通过本机环境或文件路径读取；
- overlay 是否包含 `installerHooks`；
- 最终 `installer.nsi` 是否包含 hook；
- `.exe` 和 `.sig` 是否同时生成；
- 发布资产的 SHA-256 是否记录。

### 5.4 测试规则

自动化测试分成四层：

1. Node 业务与更新流程测试；
2. Rust 进程生命周期测试；
3. 配置、NSIS hook 和构建 overlay 契约测试；
4. Windows 实机安装、覆盖安装、自动更新和数据恢复验收。

## 7. 最重要的经验

“源码里有处理逻辑”不等于“最终安装包执行了处理逻辑”。对于 Windows 安装和自动更新，必须沿着真实数据流逐层验证：

```text
应用退出
  → sidecar 回收
  → 安装器启动
  → NSIS hook 执行
  → 文件句柄释放
  → 文件覆盖
  → 签名校验
  → 应用重启
```

以后同类问题首先检查实际进程和最终安装器脚本，再决定是否修改代码；先证据定位，再做单一修复，并用真实安装包复验。
