# 教师工作台 v0.9.0 安装版闪退问题排查与修复总结

本次文件占用问题的完整复盘与防复发规则另见：[v0.9.0 安装更新文件占用问题复盘与经验教训](2026-08-31-v0.9.0安装更新文件占用问题复盘与经验教训.md)。

## 1. 问题背景

v0.9.0 首次引入 Windows x64 安装版和 Tauri 自动更新能力。安装版与绿色便携版不同：

- 程序安装到用户选择的目录；
- 用户数据放在 `%LOCALAPPDATA%\TeacherWork\data`；
- 安装版内置 Node 运行时和本地 server；
- 安装版启用 Tauri updater，便携版暂时继续手动升级。

本次本机验收时，安装器可以完成安装，但双击桌面图标后窗口短暂出现，随后立即消失。由于 Windows GUI 程序没有控制台窗口，用户看到的现象就是“闪退”。

## 2. 排查过程

### 2.1 先确认安装资源是否完整

第一轮检查发现，安装包虽然包含了部分后端文件，但没有按照桌面程序实际查找的资源布局落地。程序需要的路径是：

```text
安装目录\resources\runtime\node.exe
安装目录\resources\app\server\index.js
```

如果这些文件缺失，主程序无法启动内置 Node 服务，前端也就无法正常工作。

修复内容：

- 新增 `scripts/prepare-tauri-runtime.mjs`，在构建前准备安装版运行时目录；
- 将当前 Node 可执行文件复制为安装包内的 `runtime/node.exe`；
- 将 server 和生产依赖复制到 `app/server`；
- 修改 `scripts/build-tauri.mjs`，将准备好的运行时目录映射到 Tauri 的 `resources/`；
- 重新构建并确认安装包内确实存在上述两个关键路径。

这解决了“安装后找不到内置运行时”的问题，但重新验收时仍然出现闪退，说明还存在第二个独立问题。

### 2.2 增加持久化运行日志

仅依靠窗口是否出现无法判断桌面程序在哪一步退出，因此在 Rust 桌面入口增加了持久化运行日志：

```text
%LOCALAPPDATA%\TeacherWork\data\logs\desktop-runtime.log
```

日志记录以下阶段：

- 内置后端是否启动成功；
- Tauri `setup` 是否开始和完成；
- `process` 插件是否初始化成功；
- `updater` 插件是否初始化成功；
- 窗口关闭、销毁和进程退出事件。

这样即使 GUI 程序没有控制台，也可以根据最后一条日志定位退出阶段。

### 2.3 根据日志定位真正根因

实际日志显示：

```text
backend ready port=...
process plugin complete
updater plugin failed: ... The configured updater endpoint must use a secure protocol like `https`.
```

因此真正的退出链路是：

```text
后端启动成功
    ↓
Tauri setup 开始
    ↓
process 插件初始化成功
    ↓
updater 插件读取配置
    ↓
发现更新地址是 http://127.0.0.1:...
    ↓
Tauri 拒绝不安全的 HTTP endpoint
    ↓
setup 失败，GUI 进程退出
```

根因不是数据库、Node sidecar 或 Windows 安装目录，而是本地测试构建曾经注入了 HTTP 更新地址。Tauri updater 要求更新 endpoint 使用 HTTPS；在 `windows_subsystem = "windows"` 的 GUI 构建中，初始化错误没有控制台展示，于是表现为瞬间闪退。

## 3. 修复措施

### 3.1 构建入口强制校验 HTTPS

在 `scripts/build-tauri.mjs` 中加入更新地址校验：

- 必须是合法 URL；
- 必须使用 `https:`；
- 构建阶段直接拒绝 `http://127.0.0.1`、`http://localhost` 等地址。

本地验收使用 HTTPS 占位地址，仅用于验证 Tauri updater 可以初始化；正式构建必须注入真实的 HTTPS 域名。

### 3.2 保留 updater 公钥和地址的构建时注入

生产信息不写入仓库，构建时通过环境变量注入：

```powershell
$env:TAURI_UPDATER_PUBLIC_KEY = '<正式更新公钥>'
$env:TEACHER_WORK_UPDATE_ENDPOINT = 'https://你的域名/teacher-work/stable/latest.json'
npm run package:installed
```

签名私钥只存在于发布电脑或 CI 的安全环境中，不放进代码仓库、安装包或日志。

### 3.3 增加回归保护

已增加安装版配置测试，保证以后构建时：

- 安装版 updater endpoint 不能是 HTTP；
- 资源目录必须包含运行时和 server；
- 测试密钥下的安装包仍能完成构建和校验。
- 生产签名测试包可以通过仓库外的私钥文件路径完成构建，私钥内容不会进入日志或 Git。

### 3.4 真实升级演练发现的 Vue Proxy 问题

首次使用已安装的 v0.9.0 客户端执行“备份并更新”时，检查更新可以发现 v0.9.1，但点击确认后出现：

```text
'get' on proxy: property 'Symbol(nativeUpdate)' is a read-only and non-configurable data property on the proxy target
```

排查确认，之前提供给本机验收的 v0.9.0 安装包是在该修复提交之前构建的旧客户端。更新结果对象内部保存了 Tauri 原生 `Update` 对象，前端把它放进普通 Vue `ref` 后发生深度代理；访问不可配置的 `Symbol(nativeUpdate)` 属性时，Vue Proxy 违反了 JavaScript Proxy 不变量，错误发生在真正下载前。

修复方式：

- `web/src/views/Changelog.vue` 使用 `shallowRef` 保存 `pendingUpdate`；
- 让 Tauri 原生更新对象保持原样，不再被 Vue 深度代理；
- 增加回归测试，防止更新页面再次使用普通 `ref` 保存原生更新对象；
- 用包含修复的代码重新构建 v0.9.0 安装包，文件已复制到 `E:\工作台测试\教师工作台_0.9.0_修复Proxy-CloudBase测试-setup.exe`。

这次问题也说明：CloudBase 上传新版本后，已经安装的旧客户端不会自动获得客户端代码修复；如果旧客户端在“下载更新之前”就失败，必须先用修复版安装包覆盖安装，再重新进行升级演练。

### 3.5 真实升级演练发现的 Windows 文件占用问题

使用包含 3.4 修复的旧版客户端执行升级时，NSIS 安装器又出现了：

```text
Error opening file for writing:
...\resources\runtime\node.exe
...\resources\app\node_modules\better-sqlite3\build\Release\better_sqlite3.node
```

这说明更新包已经下载并启动安装器，但旧应用进程仍然占用内置 Node 和原生数据库模块。检查 Tauri updater 的 Windows 行为后确认：`downloadAndInstall()` 在 Windows 上启动 NSIS 后会负责退出当前应用；此前代码在它返回后又调用了一次 `relaunch()`，导致安装器和应用进程发生重叠，形成文件替换竞争。

修复方式：

- Windows 安装版不再在 `downloadAndInstall()` 后手动调用 `relaunch()`；
- 由 Tauri updater 启动安装器并负责退出旧进程；
- 增加回归测试，确保更新安装流程不会额外触发重启；
- 重新构建同时包含 Proxy 修复和进程退出修复的 0.9.0 覆盖安装包，以及对应的 0.9.1 测试升级包。

此前选择“忽略”后启动的 0.9.1 只能视为半更新：版本号已经变成 0.9.1，但部分被占用文件可能仍来自旧包。必须先用新的 0.9.0 覆盖安装，再重新进行升级测试。

### 3.6 再次演练确认后台服务退出存在竞态

使用仅移除 `relaunch()` 的安装包再次演练时，`better_sqlite3.node` 仍偶发被 NSIS 报告为占用。由此确认仅依赖更新器触发应用退出仍存在退出竞态：本地 Node 后台服务可能尚未完成退出，安装器已经开始替换资源。

最终修复方式：

- 新增 Tauri `shutdown_backend` 命令，复用统一的 sidecar 关闭逻辑，执行 `kill + wait`；
- 用户确认“备份并更新”后，先完成带附件的恢复点，再显式停止后台服务；
- 后台服务停止成功后才进入 `downloadAndInstall()`，由 Windows 更新器继续负责退出应用和启动安装器；
- 新增桌面桥接、命令注册和更新页面回归断言；
- 重新构建并上传新的 0.9.1 CloudBase 测试包，新的 0.9.0 覆盖安装包为 `E:\工作台测试\教师工作台_0.9.0_修复Proxy-后台退出-CloudBase测试-setup.exe`。

### 3.7 进一步审查确认存在残留进程与安装覆盖竞态

在 0.9.0 和 0.9.1 安装过程中仍出现以下 NSIS 提示：

```text
Error opening file for writing:
...\resources\runtime\node.exe
...\resources\app\node_modules\better-sqlite3\build\Release\better_sqlite3.node
```

这不是“安装包缺文件”，而是 Windows 正在执行原地覆盖时，旧版本的 `node.exe` 或主程序仍持有目标文件。日志和进程检查还发现，旧实现只保存当前启动的 `Child`；如果主程序异常退出、重复启动或更新器与旧进程短暂重叠，系统中可能留下当前应用目录对应的 Node 进程，下一次安装就会再次被锁定。安装器中的“忽略”只会跳过该文件，可能形成新旧文件混合的半更新状态，不能作为正常修复方案。

本次最终修复在三个边界同时加固：

- NSIS `NSIS_HOOK_PREINSTALL`：复制文件前关闭 `teacher-work.exe` 进程树，并通过 `ExecutablePath` 精确匹配当前 `$INSTDIR\resources\runtime\node.exe`；绝不按名称结束其他项目的 `node.exe`。
- 安装版启动保护：使用 Windows 命名互斥体 `Local\TeacherWork-Installed-v1`，第二个安装版实例不启动后端，避免重复实例互相占用端口、SQLite 和资源文件。
- 后台服务托管：使用 Windows Job Object 的 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 管理内置 Node；正常关闭执行 `kill + wait`，主程序异常退出时由系统连带回收进程；启动前还会清理精确匹配本安装目录的残留 Node。

便携版继续保留同级 `data` 目录和手动升级方式，但共用确定性的后台 `kill + wait` 关闭逻辑。安装版数据目录、备份目录和恢复点均不在 NSIS 清理范围内。

### 3.8 二次验收发现 NSIS hook 注入边界并修复

用户使用首个“进程保护最终验收包”时，安装器仍报告上述两个文件被占用。对本机进程和构建产物复核后确认：当前电脑确实存在孤儿进程 `node.exe`，其完整路径为：

```text
C:\Users\kangt\AppData\Local\教师工作台\resources\runtime\node.exe
```

精确路径查询可以识别该进程，因此根因不是路径判断错误，而是安装器构建使用第二份 updater 配置时，NSIS hook 没有被显式带入最终配置，且原 hook 的嵌套 PowerShell `-Filter` 引号不够稳健。

二次修复包括：

- `scripts/build-tauri.mjs` 在生成 updater 配置时显式写入 `bundle.windows.nsis.installerHooks`，确保多配置合并后最终 NSIS 安装器仍携带 hook；
- hook 改用普通 PowerShell 条件筛选，避开嵌套 `-Filter` 引号解析；
- 精确结束当前安装目录的 Node 后等待其退出；
- 同时覆盖 `NSIS_HOOK_PREINSTALL` 和 `NSIS_HOOK_PREUNINSTALL`；
- 增加构建脚本契约测试和 `Wait-Process` 回归断言。

二次修复包为：`E:\工作台测试\教师工作台_0.9.0_进程保护二次修复-setup.exe`。构建后检查确认生成的 `tauri.updater.conf.json` 已明确包含 `src-tauri/windows/hooks.nsh`。

### 3.9 二次修复包实测仍失败：NSIS 与 PowerShell 变量转义遗漏

用户实际运行二次修复包时，安装器仍在覆盖以下文件时提示 `Error opening file for writing`：

```text
C:\Users\kangt\AppData\Local\教师工作台\resources\app\node_modules\better-sqlite3\build\Release\better_sqlite3.node
C:\Users\kangt\AppData\Local\教师工作台\resources\runtime\node.exe
```

当时本机存在一个父进程已经退出的孤儿后台进程：

```text
PID 14124
C:\Users\kangt\AppData\Local\教师工作台\resources\runtime\node.exe
```

手动结束这个精确路径匹配的进程后，取消原安装并重新运行同一个二次修复包，安装立即成功且不再弹出文件写入错误。这证明文件锁根因判断正确，同时证明 NSIS hook 在原包中没有成功完成 PowerShell 清理。

进一步复核发现，NSIS 字符串中的 `$` 会先由 NSIS 解析；PowerShell 变量必须写成 `$$root`、`$$node`、`$$_.Name`、`$$_.ExecutablePath` 和 `$$_.ProcessId`，才能把单个 `$` 原样传给 PowerShell。原 hook 漏掉了这层转义，导致安装器中的清理命令与源码看到的命令不一致。

本次三次修复改动：

- 先增加回归测试，要求 NSIS hook 中所有 PowerShell 变量都使用双美元符号转义；
- 将清理命令中的 PowerShell 变量全部改为 NSIS 安全写法；
- 保留当前安装目录精确匹配、强制结束和 `Wait-Process`，不扩大到其他 Node 进程；
- 保留 `NSIS_HOOK_PREINSTALL` 与 `NSIS_HOOK_PREUNINSTALL` 两个生命周期入口。

相关依据：NSIS 官方说明 PowerShell 命令中的 `$` 需要写成 `$$`，Tauri 官方说明 `NSIS_HOOK_PREINSTALL` 会在复制文件前执行。

## 5. 经验与后续门禁

以后每次发布安装版都必须同时检查三层内容：

1. **资源层**：`resources\runtime`、`resources\app` 和生产依赖完整；
2. **初始化层**：后端、数据库迁移、`process` 插件和 `updater` 插件全部成功；
3. **公网发布层**：真实 HTTPS endpoint 可访问，安装包、`.sig` 和 `latest.json` 的版本、签名和哈希一致。

当前 CloudBase 自动更新仍处于测试目录：检查更新、更新前备份、Proxy 修复、后台服务退出和 Windows 文件占用修复已经完成；还需用本次新构建的 v0.9.0 覆盖安装后完成一次真实下载、验签、安装、重启和数据保留验收。正式发布前仍需配置正式更新域名、完成 Authenticode 签名、从公网重新下载复核，并最后才把 `latest.json` 指向正式用户。
