# 教师工作台 v0.9.0 自动更新部署方案对比与操作流程

## 1. 先说结论

教师工作台的自动更新只需要托管公开的静态文件，不需要把班级、学生、成绩或附件上传到云端。

需要公开访问的文件只有：

```text
stable/latest.json                         最新版本清单
releases/v0.9.0/教师工作台_0.9.0_x64-setup.exe  安装包
releases/v0.9.0/教师工作台_0.9.0_x64-setup.exe.sig  Tauri 签名
releases/v0.9.0/checksums.json             SHA-256 校验清单，可选但建议保留
```

客户端启动后请求 `stable/latest.json`。清单告诉客户端当前版本、安装包下载地址和签名；客户端内置公钥验证签名，验证通过后才允许安装。

因此：

- 自有服务器方案的核心是“配置一个 HTTPS 静态目录”；
- CloudBase 方案的核心是“配置一个 HTTPS 静态托管目录”；
- 两种方案都不需要 CloudBase 数据库、云函数、登录系统或业务 API。

## 2. 两种方案对比

| 对比项 | 自有服务器 + 自有域名 | 腾讯云 CloudBase 静态托管/COS |
|---|---|---|
| 控制力 | 最高，目录、Nginx、备份和发布脚本都自己控制 | 较高，文件由腾讯云托管，底层运维更少 |
| 国内访问 | 取决于服务器地域、线路、带宽和域名备案情况 | 通常更省运维，可结合腾讯云网络和 CDN |
| 初始配置 | 需要 HTTPS、Web 服务器、目录权限和缓存规则 | 需要 CloudBase 环境、静态托管或 COS、域名和权限配置 |
| 后续发布 | 上传文件即可，适合脚本化和 CI | 上传文件即可，控制台操作较直观，也可用 CLI/MCP |
| 大文件下载 | 消耗自有服务器出口带宽 | 更适合对象存储/CDN 分发大安装包 |
| 故障排查 | 日志和故障原因完全自己掌握 | 需要同时看 CloudBase、域名、CDN 和权限状态 |
| 平台依赖 | 较低，迁移到其他服务器容易 | 对 CloudBase 的环境和托管配置有一定依赖 |
| 适合情况 | 已有稳定服务器、熟悉 Nginx、希望完全控制 | 希望少维护服务器，已有腾讯云账号和环境 |

### 简单选择建议

- 如果你的服务器已经有稳定 HTTPS 网站，并且带宽足够，优先自有服务器，流程最透明；
- 如果不想维护 Nginx、证书、文件权限和服务器安全，优先 CloudBase 静态托管；
- 如果后续用户较多、安装包下载量较大，CloudBase COS/CDN 或“自有域名 + 对象存储/CDN”更合适；
- 无论选择哪一种，客户端里只写你的自有域名，不把 CloudBase 默认域名作为唯一长期地址。

## 3. 共同的发布流程

两套方案前面的构建和签名流程完全相同。

### 第一步：准备生产签名信息

保留现有 Tauri updater 公钥，并准备生产签名私钥。私钥只放在发布电脑或 CI 的安全变量中。

```powershell
$env:TAURI_UPDATER_PUBLIC_KEY = '<正式更新公钥>'
$env:TEACHER_WORK_UPDATE_ENDPOINT = 'https://你的域名/teacher-work/stable/latest.json'
```

`TEACHER_WORK_UPDATE_ENDPOINT` 必须使用 HTTPS，不能使用 HTTP 或本地回环地址。

### 第二步：构建安装包

```powershell
npm run package:installed
```

构建输出包含安装包和 Tauri 签名文件。正式构建时不要使用本地测试私钥。

### 第三步：生成更新清单和哈希

使用仓库里的 `scripts/generate-update-manifest.mjs` 生成：

- `latest.json`；
- `checksums.json`。

生成器会检查版本、安装包、签名文件和资源地址，但不会保存签名私钥。

### 第四步：按顺序上传

必须先上传版本目录中的安装包、`.sig` 和 `checksums.json`，确认可以下载后，最后才上传或替换 `stable/latest.json`。

不能先发布 `latest.json`，否则客户端可能先发现新版本，但下载文件还没有上传完成。

### 第五步：公网复核

至少检查：

- `latest.json` 可以通过 HTTPS GET 获取；
- JSON 中的版本是预期版本；
- 安装包 URL 可以下载完整文件；
- `.sig` 内容非空；
- 下载文件的 SHA-256 与 `checksums.json` 一致；
- 在一台已安装旧版本的 Windows 电脑上能发现新版本；
- 签名正确时可以安装，签名错误时必须拒绝安装。

## 4. 方案 A：自有服务器和域名

### A-1. 服务器上准备静态目录

可以使用 Nginx、Caddy 或已有 Web 服务。建议目录结构如下：

```text
/var/www/teacher-work-updates/
├─ stable/
│  └─ latest.json
└─ releases/
   └─ v0.9.0/
      ├─ 教师工作台_0.9.0_x64-setup.exe
      ├─ 教师工作台_0.9.0_x64-setup.exe.sig
      └─ checksums.json
```

实际目录可以不同，关键是 URL 结构稳定，并且版本目录不可变。发布 v0.9.1 时新增 `releases/v0.9.1/`，不要覆盖 v0.9.0 的安装包。

### A-2. 配置 HTTPS 域名

例如：

```text
https://updates.example.com/teacher-work/stable/latest.json
```

需要完成：

1. DNS 将 `updates.example.com` 指向服务器；
2. Web 服务器配置 HTTPS 证书；
3. 配置静态文件根目录；
4. 确认普通用户可以读取文件；
5. 确认服务器不会给 `.json`、`.sig` 或 `.exe` 返回登录页、错误页或重定向到 HTTP。

建议缓存策略：

- `stable/latest.json`：不缓存或只缓存很短时间；
- `releases/v0.9.0/*`：可以长缓存，因为版本目录不可变；
- 安装包支持断点续传和稳定下载。

### A-3. 上传发布资产

先上传：

```text
releases/v0.9.0/教师工作台_0.9.0_x64-setup.exe
releases/v0.9.0/教师工作台_0.9.0_x64-setup.exe.sig
releases/v0.9.0/checksums.json
```

确认三个文件可访问且哈希正确后，再上传：

```text
stable/latest.json
```

### A-4. 自有服务器方案的优点和维护责任

优点：

- 不依赖某个云平台的默认域名；
- 版本目录、备份、权限和发布脚本完全可控；
- 以后切换服务器时，只需保持域名不变。

需要自己负责：

- HTTPS 证书续期；
- 服务器系统和 Web 服务安全更新；
- 磁盘空间、带宽和备份；
- 文件权限和错误页面配置；
- 公网下载故障排查。

## 5. 方案 B：腾讯云 CloudBase

### B-1. 选择托管方式

CloudBase 侧可以采用静态网站托管，或者使用 COS/对象存储承载更新文件，再通过自定义域名提供访问。

本项目只需要静态文件，不建议为了自动更新创建数据库或云函数。

### B-2. 准备 CloudBase 环境

需要准备：

- 腾讯云账号；
- 一个明确的 CloudBase 环境；
- 环境的正式 EnvId；
- 静态托管或 COS 存储位置；
- 自定义域名和 HTTPS 证书；
- 具有上传权限的账号或部署密钥。

操作 CloudBase 前必须先确认正式 EnvId，不能只凭环境昵称操作，避免把文件上传到错误环境。

### B-3. 创建更新文件目录

在 CloudBase 静态托管或 COS 中建立与自有服务器相同的逻辑结构：

```text
teacher-work/
├─ stable/
│  └─ latest.json
└─ releases/
   └─ v0.9.0/
      ├─ 教师工作台_0.9.0_x64-setup.exe
      ├─ 教师工作台_0.9.0_x64-setup.exe.sig
      └─ checksums.json
```

如果是首次创建 CloudBase 静态应用，应按 CloudBase 的首次创建流程建立应用；后续版本只更新已有静态资源，不要重复创建应用。

### B-4. 配置自定义域名和缓存

建议使用自己的域名，例如：

```text
https://updates.example.com/teacher-work/stable/latest.json
```

需要确认：

- 自定义域名绑定到了正确的 CloudBase 静态托管或 COS；
- HTTPS 证书有效；
- `latest.json` 不被 CDN 长时间缓存；
- 版本目录可以长缓存；
- `.exe` 下载不会被权限规则拦截；
- 返回内容不是 CloudBase 登录页或错误页。

### B-5. 上传发布资产

流程与自有服务器相同：

1. 先上传 `releases/v0.9.0/` 中的安装包、`.sig` 和 `checksums.json`；
2. 使用公网自定义域名下载验证；
3. 最后上传 `stable/latest.json`；
4. 再用旧版安装程序执行一次“发现更新—下载—签名校验—安装—重启”验收。

CloudBase 的控制台适合第一次操作和人工确认；后续可以再使用 CloudBase CLI、MCP 或 CI 做重复发布，但每次都要明确指定 EnvId 并验证上传结果。

### B-6. CloudBase 方案的优点和维护责任

优点：

- 不需要自己维护 Nginx 和服务器系统；
- 静态文件托管和公网访问配置更集中；
- 更容易继续接入腾讯云 COS、CDN 和监控；
- 适合不希望处理服务器运维的场景。

需要自己负责：

- CloudBase 环境和域名配置；
- 上传权限、账号安全和部署密钥；
- 静态托管/COS 的费用和访问策略；
- CDN 缓存刷新；
- CloudBase、域名和证书之间的故障排查。

## 6. 对本项目的建议顺序

为了降低风险，建议按下面顺序推进：

1. 先选定一个自己的更新域名，例如 `updates.你的域名`；
2. 先在选定平台创建空的 HTTPS 静态目录；
3. 用测试文件验证 `latest.json`、安装包和 `.sig` 的公网下载；
4. 再用生产签名私钥构建 v0.9.0；
5. 上传 v0.9.0 资产并从公网复核；
6. 最后发布 `stable/latest.json`；
7. 在旧版本安装环境中完成一次真实自动更新；
8. 确认成功后，再把 v0.9.0 作为正式首个自动更新版本。

目前最需要你提供的不是代码，而是以下选择：

- 采用自有服务器还是 CloudBase；
- 准备用作更新地址的域名或子域名；
- 如果选 CloudBase，使用的正式 EnvId；
- 如果选自有服务器，服务器上是否已经有 HTTPS 网站和可上传目录。

签名私钥不要直接发到聊天中。后续只需要在本机或发布环境中配置，不写入仓库。
