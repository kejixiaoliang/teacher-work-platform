# 教师工作台 v0.9.0 便携版关闭生命周期问题与修复记录

> 记录日期：2026-08-29  
> 适用版本：v0.9.0 及后续 Windows 桌面版本

## 1. 问题现象

在 Windows 便携包中通过窗口关闭按钮退出时，`CloseMainWindow()` 可以返回成功，但主程序进程在等待时间内没有退出，内置 `resources/runtime/node.exe` 也会继续留在任务管理器中。这个现象在 v0.9.0 新构建包和已知的 v0.8.0 便携包中都可以复现，因此属于桌面关闭生命周期的历史问题，并非安装版路径策略单独引入的问题。

这会直接影响 v0.9.0 的自动更新基础：更新器只有在主程序和本地 Node 服务都释放文件句柄后，才能安全替换程序文件；残留 sidecar 还会造成 SQLite、资源目录和端口继续被占用。

## 2. 根因

原实现把关闭逻辑分散在多个 Tauri 事件路径中：窗口关闭事件、`RunEvent::WindowEvent`、`ExitRequested` 和 `Exit` 都各自尝试终止子进程，其中部分路径还直接调用 `std::process::exit(0)`。

这带来两个问题：

1. 强制终止发生在 Tauri 正常退出事件链之外，窗口关闭请求不一定能完成完整的应用退出收尾。
2. `Child::kill()` 后没有统一 `wait()`，并且子进程状态一直保存在 `Mutex<Child>` 中，无法通过一次幂等的清理动作明确完成回收。

## 3. v0.9.0 修复方案

Rust 桌面层现在遵循单一关闭生命周期：

```text
窗口 CloseRequested
  → Tauri RunEvent 统一处理
  → destroy() 强制销毁窗口
  → app_handle().exit(0)
  → RunEvent::ExitRequested / Exit
  → 取出唯一 Child
  → kill
  → wait 回收
  → Tauri 事件循环自然结束
```

具体约束如下：

- `DesktopState.child` 使用 `Mutex<Option<Child>>`，清理时先 `take()`，保证重复收到 `ExitRequested` 和 `Exit` 也不会重复操作同一个进程；
- sidecar 清理统一执行 `kill()` 后的 `wait()`；
- 窗口关闭进入 `RunEvent::WindowEvent` 后使用 `destroy()` 绕过 WebView 的 `beforeunload` 阻塞，再请求 Tauri 退出；不在回调中调用 `std::process::exit(0)`；
- Node 服务继续保留 `SIGINT` 和 `SIGTERM` 处理，用于释放 HTTP 服务和 SQLite 连接；
- 便携版和安装版共用这套关闭语义，避免更新版再次出现文件占用。

## 4. 回归测试与验收

自动化回归包括：

- Node 退出契约测试：确认不存在强制退出调用，且存在 `Option<Child>`、`take()` 和 `wait()`；
- Rust 单元测试：确认 sidecar 可被终止、等待回收，并且清理操作具有幂等性；
- 最终 Windows 便携包 QA：启动解压后的 EXE，正常关闭窗口，确认主程序退出且同目录 `resources/runtime/node.exe` 不残留。

目前自动化契约和 Rust 单元测试已通过，便携包也可以构建。当前执行环境通过命令行启动时只暴露无标题的 `Tao Thread Event Target` 消息窗口，无法完成真实交互式关闭；原有 QA 的 `Process.MainWindowHandle` 还会误指向 Windows 输入指示器窗口，已改为按 Tauri 窗口类枚举并发送关闭消息。最终 Windows 交互式验收仍需在能显示真实 Tauri 窗口的桌面会话中完成；在此之前不能把 v0.9.0 标记为关闭生命周期修复完全验收。
