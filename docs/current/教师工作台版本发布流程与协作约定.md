# 教师工作台版本发布流程与协作约定

## 1. 目的

本约定用于教师工作台后续所有版本的开发、测试、安装包构建、自动更新和发布，避免只完成代码却遗漏数据迁移、签名、安装器、更新资产或真实 Windows 验收。

默认原则：先在测试渠道验证，再进入正式发布；没有通过发布门禁，不把正式更新清单指向用户。

## 2. 以后用户只需要这样告诉我

推荐固定说法：

> 教师工作台 vX.Y.Z 功能已完成，请按版本发布流程处理。目标版本：X.Y.Z；需要发布：安装版/便携版/两者；更新渠道：测试/正式；本次主要改动：……；是否涉及数据库结构或备份格式：是/否。

如果暂时不清楚这些信息，也可以只说：

> 教师工作台新版本已完成，按默认发布流程推进，先测试，不要正式发布。

我会默认：创建独立 work tree 和 `codex/` 分支、先写计划、先走测试渠道，不直接上传生产资产。

## 3. 版本发布状态

每个版本只能按以下顺序推进：

```text
开发完成
  → 计划与风险审查
  → 代码测试通过
  → 测试包构建
  → 本机安装/更新验收
  → 测试渠道部署
  → 他人或干净环境验收
  → 发布候选包
  → 正式签名与正式部署
```

任何阶段失败都回到该阶段处理，不能用“忽略安装错误”或“测试通过所以直接发布”替代门禁。

## 4. 我每次必须执行的流程

### 阶段 A：建立版本工作区

- 从主分支创建独立 work tree；
- 创建 `codex/vX.Y.Z-主题` 分支；
- 检查主分支、当前版本和工作区是否干净；
- 阅读最近版本计划、发布清单和相关复盘文档；
- 创建本版本计划文档，写明目标、范围、风险和验收标准。

### 阶段 B：实现与验证

- 先为新行为或问题补测试；
- 运行测试并确认测试能够捕获问题；
- 再实现最小改动；
- 运行 Node、Rust、构建配置和版本契约测试；
- 检查数据库迁移、备份兼容性和安装版/便携版边界。

### 阶段 C：分阶段提交

每完成一个可验证阶段就提交一次，提交信息使用清晰的英文 Conventional Commit，例如：

```text
feat: add ...
fix: prevent ...
test: cover ...
docs: record ...
build: prepare ...
```

禁止把多个未验证的大改动堆到最后一次提交。每次提交前必须检查 `git diff --check` 和工作区状态。

### 阶段 D：构建与资产检查

安装版构建必须检查：

- 版本号在 package、Cargo、Tauri 配置和发布说明中一致；
- updater endpoint 使用 HTTPS；
- public key 与签名私钥匹配；
- 私钥只从本机安全路径或环境读取，不进入仓库、日志、截图和发布目录；
- 动态生成的 updater overlay 包含必要配置；
- 最终 `installer.nsi` 包含 NSIS hook；
- `.exe` 与 `.sig` 同时生成；
- 记录 SHA-256；
- 便携版仍不携带安装版自动更新行为。

### 阶段 E：Windows 实机验收

至少验证：

- 新安装；
- 安装后桌面图标启动；
- 关闭后再次启动；
- 覆盖安装；
- 从旧版本检查更新；
- 更新前备份数据库和附件；
- 更新后版本正确、数据和附件完整；
- 应用关闭后没有残留本版本后台进程；
- 卸载和重新安装不误删用户数据；
- 不出现 `better_sqlite3.node`、`node.exe` 等文件写入错误。

涉及 Windows 进程、文件锁、安装器或更新器的改动，源码测试通过不等于发布通过，必须增加真实安装包验收。

### 阶段 F：部署与发布

- 默认先部署到 CloudBase 测试目录；
- 测试通过后才能准备正式目录；
- 正式部署前重新使用生产签名私钥构建，不复用测试包；
- 生成并检查正式 `latest.json`、安装包、签名文件和哈希清单；
- 正式发布动作必须得到用户明确确认；
- 发布完成后记录版本、时间、资产哈希、更新地址和回滚资产。

## 5. 用户需要提供什么

通常只需要提供以下信息：

- 版本号和本次功能概要；
- 是否修改数据库结构、备份格式或用户数据；
- 发布安装版、便携版，还是两者；
- 先测试还是直接准备正式发布；
- 测试人员或测试电脑；
- 正式发布确认。

签名私钥不需要发到聊天中。只需要保证本机安全路径仍可读取，或者在需要构建时由用户在本机输入密码。

CloudBase 环境、域名和测试目录如果保持不变，也不需要每次重复提供；只有更换环境或发布地址时才需要重新确认。

## 6. 明确的安全约束

- 不把生产私钥、密码、恢复密钥、API Token 写进代码或文档；
- 不把测试更新地址误当成正式更新地址；
- 不在未确认的情况下覆盖 CloudBase 正式目录；
- 不把未完成验收的安装包发给普通用户；
- 不用“忽略”跳过安装器文件写入错误；
- 不用按名称全局结束 `node.exe`，只能精确匹配本应用安装目录；
- 不删除用户数据目录来解决安装问题；
- 不使用破坏性 Git 操作覆盖用户未提交的工作。

## 7. 当前 v0.9.0 的剩余门禁

当前分支已经完成代码修复、复盘文档、签名测试包和本机安装/自动更新验证。正式发布前仍需：

- 使用生产签名私钥重新构建；
- 完成 Windows Authenticode 代码签名；
- 在干净 Windows 10/11 x64 环境再次执行安装、启动、更新、数据恢复和卸载验收；
- 将测试渠道和正式渠道资产明确分开；
- 得到用户明确确认后再部署 CloudBase 正式更新清单。

## 8. 每次对话的最小状态报告

我在每个阶段结束时应说明：

```text
当前阶段：……
已完成：……
验证结果：……
提交：……
下一步：……
需要用户操作：……（没有则写“无”）
```

这样用户不需要了解 work tree、签名、NSIS 或 CloudBase 的内部细节，也能知道当前版本处于什么状态、下一步是否需要自己点击或测试。
