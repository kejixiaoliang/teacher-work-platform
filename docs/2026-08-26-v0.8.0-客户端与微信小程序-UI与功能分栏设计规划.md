## 一、规划结论

小程序不重新设计一套新的业务产品，也不新增与现有客户端无关的功能。本次工作只做两件事：

1. 复用现有客户端已经具备的功能；
2. 根据手机屏幕和微信小程序的交互特点，重新组织页面布局和操作路径。

核心原则是：

> 功能可以重新分栏，布局可以重新设计，数据规范、业务含义、记录 ID 和权限规则必须保持统一。

客户端和小程序的关系如下：

```text
电脑端 UI ─┐
           ├─ 统一数据规范、统一业务规则、统一 CloudBase 数据
小程序 UI ─┘
```

两端不是各自维护一套数据，而是同一套数据模型的不同界面。

## 二、设计范围与明确排除项

### 2.1 本次纳入

- 现有客户端功能的移动端重新编排；
- 三栏底部导航：概览首页、功能工作台、设置；
- 现有客户端页面名称和业务含义的复用；
- 客户端与小程序的数据字段、ID、枚举值和关联关系统一；
- 适合手机操作的列表、卡片、详情页和表单布局；
- CloudBase 数据读取、写入和同步时的统一数据契约。

### 2.2 本次不新增

除现有客户端或既定 CloudBase 规划已经存在的内容外，本版本不新增以下类型的业务功能：

- 学生端或家长端；
- 独立消息中心；
- 与现有功能无关的成长系统、积分系统或社交功能；
- 新的班级管理业务模块；
- 新的统计口径；
- 新的身份体系；
- 为了小程序而重新建立一套数据表和 ID。

兑换码、管理员后台、客户端登录和云端同步属于既定的产品基础设施规划，不属于本文件新增的小程序业务模块；其入口按既有规划放入设置或登录流程中。

## 三、现有客户端功能基线

小程序第一版的功能来源以当前客户端实际路由和使用指南为准，名称原则上保持一致。

| 客户端现有功能 | 小程序是否保留 | 移动端处理方式 |
| --- | --- | --- |
| 概览首页 | 保留 | 改为首页概览卡片和待处理列表 |
| 学生管理 | 保留 | 学生列表、搜索、详情和记录入口 |
| 座位管理 | 保留 | 优先查看，编辑操作进入独立编辑页 |
| 数据分析 | 保留 | 采用纵向图表和分段统计 |
| 成绩管理 | 保留 | 考试列表、成绩详情和基础录入 |
| 考勤管理 | 保留 | 日期切换、学生状态快速标记 |
| 表现量化 | 保留 | 规则选择、学生范围选择和记录提交 |
| 文档管理 | 保留 | 按班级或学生查看已有文档；复杂文件操作按平台能力适配 |
| 值日管理 | 保留 | 按日期或周期查看、编辑值日安排 |
| 班委学委 | 保留 | 列表查看和人员调整 |
| 课代表选择 | 保留 | 科目与学生的关联编辑 |
| 请假管理 | 保留 | 请假记录列表、详情和状态处理 |
| 家校沟通 | 保留 | 沟通记录列表和新增记录 |
| 班级设置 | 保留 | 班级切换、基础信息和模块入口配置 |
| 使用指南 | 保留 | 设置页中的帮助入口 |
| 版本更新 | 保留 | 设置页中的版本记录和更新说明 |

“保留”表示保留原有业务能力，不表示所有电脑端的复杂交互都要原样复制到手机上。

## 四、三栏信息架构

### 4.1 第一栏：概览首页

建议底部导航名称为“首页”，页面内部标题继续使用“概览首页”或“今日工作台”，与现有客户端保持关联。

首页只承载现有客户端概览内容，不发展成新的数据分析中心。

建议页面顺序：

```text
当前班级信息
  ↓
班级和学生基础概览
  ↓
今日考勤或异常提醒
  ↓
待跟进事项
  ↓
近期成绩、表现或沟通记录
  ↓
进入现有功能模块
```

首页展示的数据必须使用现有模块已有的统计口径。例如考勤数量来自考勤数据，待跟进事项来自跟进记录，不能因为小程序需要首页卡片而重新定义统计规则。

### 4.2 第二栏：功能工作台

建议底部导航名称为“工作台”。这里集中放置现有业务模块，采用分组列表或紧凑卡片，不增加新的业务入口。

建议分组如下：

#### 班级与学生

- 班级设置；
- 学生管理；
- 座位管理；
- 班委学委；
- 课代表选择。

#### 日常记录

- 考勤管理；
- 请假管理；
- 值日管理；
- 表现量化；
- 跟进事项；
- 家校沟通。

#### 成绩与资料

- 成绩管理；
- 数据分析；
- 文档管理。

分组只是导航组织方式。模块名称、数据关系、权限和业务规则仍然沿用客户端现有实现。

### 4.3 第三栏：设置

建议底部导航名称为“设置”。这里放系统、数据和帮助类入口，不放新的班级业务。

建议内容：

- 当前微信身份和教师授权状态；
- CloudBase 数据同步状态；
- 数据导入、备份和恢复；
- 电脑端绑定或登录入口；
- 兑换码和授权状态；
- 版本更新；
- 使用指南；
- 联系作者；
- 隐私、数据说明和关于软件。

其中数据导入、备份和同步属于数据基础设施入口，应继续遵守现有兼容格式，不因页面移动端化而改变导入格式。

## 五、客户端与小程序的布局适配原则

### 5.1 保持一致的内容

- 页面和功能名称；
- 字段显示名称；
- 状态名称和状态值；
- 学生、班级、成绩、考勤等记录的关联关系；
- 操作后的业务结果；
- 错误提示的含义；
- 权限控制范围；
- 客户端已有的视觉风格和颜色语言。

### 5.2 允许变化的内容

- 侧边栏改为底部导航；
- 多栏表格改为纵向列表；
- 右侧详情面板改为独立详情页；
- 弹窗编辑改为页面或底部弹层；
- 批量操作改为分步骤操作；
- 桌面端的宽表格改为横向滚动或分组详情；
- 桌面端图表改为适合窄屏的纵向图表。

### 5.3 移动端不应做的事情

- 不为了节省页面而删除原有数据字段；
- 不把多个原有状态合并成含义不明确的新状态；
- 不将原有功能改名为新的产品概念；
- 不把复杂数据直接压缩成无法追溯的摘要；
- 不在小程序端私自生成另一套业务 ID；
- 不把本地 SQLite 表结构直接当作小程序页面数据契约。

## 六、统一数据和 ID 规则

### 6.1 数据规范优先级

UI 设计不得反向修改已经确定的数据规范。页面设计、接口设计和同步实现必须依次服从：

```text
永久兼容规则
  ↓
统一交换格式和 CloudBase 数据契约
  ↓
现有客户端业务语义
  ↓
小程序页面布局
```

如果页面设计与数据规范发生冲突，优先调整页面设计。

### 6.2 ID 必须保持统一

客户端、小程序、JSON 交换文件和 CloudBase 对同一条业务记录必须使用同一套稳定身份规则。

重点包括：

- `datasetId`：数据集身份；
- `classUuid` 或统一班级 ID：班级身份；
- `studentUuid` 或统一学生 ID：学生身份；
- `recordUuid`：考勤、表现、沟通、跟进等记录身份；
- `importBatchId`：导入批次身份；
- `ownerId`：教师数据归属身份。

CloudBase 的 `_id` 只作为云端文档内部标识，不能替代跨端稳定 ID。本地 SQLite 的旧整数 `id` 只能作为本地兼容字段，不能作为跨端同步主键。

### 6.3 字段和枚举必须统一

两端必须使用统一的字段名称、字段类型、空值规则、日期规则和状态枚举。小程序显示文字可以做移动端排版，但提交给云端的字段不得改名或改义。

例如：

```text
客户端学生记录 ─┐
                 ├─ 同一个 studentUuid
小程序学生记录 ─┘
```

不能因为小程序采用不同的页面模型，就创建 `student_id`、`class_id` 等另一套映射并长期保存。

## 七、现有功能到小程序页面的映射

### 7.1 学生管理链路

```text
工作台 → 学生管理 → 学生列表 → 学生详情
                         ├─ 基本资料
                         ├─ 成绩记录
                         ├─ 表现量化记录
                         ├─ 跟进事项
                         └─ 家校沟通
```

学生详情页是移动端的主要承载页面，但只聚合已有记录，不创建新的“学生成长档案”业务概念。

### 7.2 日常管理链路

```text
首页 → 今日考勤 → 学生状态快速操作
工作台 → 请假管理 → 请假记录
工作台 → 值日管理 → 当前值日安排
工作台 → 表现量化 → 规则、对象、记录
```

### 7.3 成绩和分析链路

```text
工作台 → 成绩管理 → 考试 → 科目 → 成绩
工作台 → 数据分析 → 现有统计和趋势
```

数据分析页面只展示现有客户端已有的统计指标。若某项图表在手机上不适合展示，应调整图表布局或拆分页面，不应改变指标定义。

### 7.4 班级事务链路

```text
工作台 → 班级设置
        ├─ 班委学委
        ├─ 课代表选择
        ├─ 座位管理
        ├─ 值日管理
        └─ 文档管理
```

## 八、视觉设计执行要求

小程序 UI 应从现有客户端提取并复用以下设计资产：

- 主色和辅助色；
- 页面背景色；
- 卡片和表格的边界风格；
- 标题、正文、辅助文字的层级；
- 成功、警告、异常和禁用状态颜色；
- 按钮、标签、输入框和空状态的视觉语言；
- 页面间距和信息密度。

如果现有客户端没有集中定义设计令牌，应先从当前 CSS 和主要页面提取一份简短的 UI 令牌说明，再开始小程序页面实现。不能在未核对客户端风格的情况下重新引入完全不同的主题。

微信小程序的底部导航、页面返回、加载、空状态和错误状态遵循微信平台交互习惯，但平台适配不能改变业务内容和数据契约。

## 九、实施阶段

### 阶段一：功能基线确认

- 以 `web/src/router.js` 和现有页面为准登记功能清单；
- 检查使用指南中的功能名称是否与路由一致；
- 标记桌面端复杂功能在手机端的适配方式；
- 确认不新增业务模块。

### 阶段二：数据映射确认

- 为每个小程序页面标记读取和写入的统一数据集合；
- 标记页面使用的 `datasetId`、班级 ID、学生 ID 和记录 ID；
- 校验字段、枚举、时间和空值规则；
- 确保页面设计不会产生新的临时主键。

### 阶段三：信息架构和视觉规格

- 固定三栏名称和页面入口；
- 固定功能分组；
- 从客户端提取颜色、字体、间距和状态样式；
- 完成首页、工作台和设置的低保真页面结构；
- 使用现有功能名称进行页面标注。

### 阶段四：小程序页面实现

建议顺序：

1. 三栏导航和基础页面框架；
2. 首页概览；
3. 工作台功能目录；
4. 班级和学生列表；
5. 学生详情及已有记录入口；
6. 考勤、表现量化和跟进事项；
7. 成绩、分析、班级事务和资料页面；
8. 设置、导入、备份、同步和帮助页面。

### 阶段五：跨端一致性验收

- 同一教师在客户端和小程序看到相同的班级归属；
- 同一学生的稳定 ID 在两端一致；
- 客户端导出的数据可以按既定规则进入小程序和 CloudBase；
- 小程序新增记录可以被客户端按同一 ID 识别；
- 历史 v0.7.0 数据继续可以导入；
- 重复导入不会制造重复业务记录；
- UI 变化没有改变原有统计口径。

## 十、验收标准

### 功能范围

- 所有小程序业务入口都能追溯到现有客户端功能；
- 没有未经确认的新业务模块；
- 三栏只是导航重组，不造成重复功能或功能分叉。

### 数据一致性

- 客户端和小程序使用同一套数据字段和 ID 规则；
- `ownerId`、`datasetId`、班级 ID、学生 ID 和记录 ID 关联正确；
- 页面操作不绕过统一 CloudBase 接口和权限规则；
- 小程序不直接依赖本地 SQLite 的内部实现；
- 旧版 JSON/ZIP 兼容规则不因 UI 改造而改变。

### 交互体验

- 首页可以快速查看现有工作台重点信息；
- 工作台可以找到所有已纳入的小程序功能；
- 设置页可以找到数据、登录、版本和帮助入口；
- 电脑端用户能够凭借相同的名称和视觉风格理解小程序；
- 手机端不会出现必须依赖宽屏表格才能完成的阻塞操作。

## 十二、最终决策摘要

```text
使用现有客户端风格
使用现有客户端功能
使用现有客户端名称
使用统一数据模型
使用统一 ID 和字段
使用统一 CloudBase 数据
只重新设计手机端布局
不新增无关业务功能
```

后续小程序 UI 设计和实现均以本规划为边界。若需要增加新功能，必须单独说明业务必要性、数据影响和版本范围，不能借 UI 设计之名直接加入。
