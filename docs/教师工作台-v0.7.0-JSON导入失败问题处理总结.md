# 教师工作台 V0.7.0 JSON 导入失败问题处理总结

## 1. 问题背景

本次问题涉及教师工作台最重要的数据迁移链路：

1. 在旧工作台中导出 JSON 数据。
2. 新建一个全新的、没有班级的教师工作台。
3. 使用“更新导入 JSON”或“从备份恢复”导入之前导出的文件。
4. 导入后应恢复班级、学生、成绩、考勤、座位、文档记录等结构化数据。

实际过程中出现过以下现象：

- 页面提示“更新导入完成：新增 1 个班级、12 名学生”。
- 但首页仍显示“请先到「班级设置」创建班级”。
- 班级列表为空，学生和其他业务数据也没有显示。
- 部分情况下出现错误：

  ```text
  UNIQUE constraint failed: assessment_categories.name
  ```

这说明该问题不是普通的页面显示问题，而是数据导入链路中同时存在后端事务和数据合并两个缺陷。

## 2. 最终确认的三个根因

### 2.1 “更新导入 JSON”事务没有真正执行

文件：`server/routes/backup.js`

原来的代码创建了 SQLite 事务函数，但没有调用它：

```js
const inserted = db.transaction(() => {
  // 插入数据
});
return inserted;
```

`db.transaction()` 返回的是一个待执行的函数。仅仅创建这个函数不会写入数据库，因此：

- 路由可以继续执行并返回成功响应。
- 返回数量来自导入 JSON 的内存结构，而不是数据库实际写入结果。
- 页面收到“新增成功”的提示。
- 数据库实际上仍然为空。

这就是“提示成功但什么都没有”的直接原因。

修复后改为：

```js
const insertTransaction = db.transaction(() => {
  // 插入数据
});
insertTransaction();
return true;
```

### 2.2 全新工作台并非所有数据表都为空

虽然全新工作台没有班级，但系统初始化时会创建默认评价数据：

- `assessment_categories`：评价分类。
- `assessment_items`：评价项目。

其中 `assessment_categories.name` 具有唯一约束，`assessment_items` 具有“分类 + 名称”唯一约束。

因此，导入一个包含默认评价分类的 JSON 时，如果简单地执行普通 INSERT，就会触发：

```text
UNIQUE constraint failed: assessment_categories.name
```

整个更新事务会回滚，班级和学生也会一起导入失败。

### 2.3 页面存在导入请求与启动请求的竞态

应用启动时会异步加载班级列表。如果启动阶段的旧请求在导入完成后才返回，旧请求可能把刚刚导入的新班级列表覆盖为空列表。

因此，即使后端已经成功写入数据，页面也可能短暂或持续显示空工作台。

## 3. 修复方案

### 3.1 正确执行更新导入事务

在 `insertAsNewDataset()` 中显式调用 SQLite 事务函数。

这样可以保证：

- 所有数据真正写入数据库。
- 任意一张表发生错误时，整个更新事务回滚。
- 接口返回成功时，数据库中确实已经存在对应数据。

### 3.2 对默认评价分类进行安全合并

更新导入时，按照以下规则处理评价数据：

#### 评价分类

对 `assessment_categories` 按 `name` 查找：

- 如果本地不存在同名分类：插入新分类。
- 如果本地已有同名分类：复用本地分类 ID。
- 建立“导入文件中的旧 ID → 当前数据库 ID”的映射。

#### 评价项目

对 `assessment_items` 按以下组合查找：

```text
category_id + name
```

- 如果本地不存在：插入新评价项目。
- 如果本地已存在：复用本地评价项目 ID。
- 将后续评价记录中的旧 `item_id` 映射到当前 ID。

这样既不会破坏系统默认数据，也不会造成外键失效。

### 3.3 增加前端班级列表请求序列保护

文件：`web/src/store.js`

为 `loadClasses()` 增加请求序列号：

```js
let classesLoadSeq = 0;
```

每次加载班级列表时生成新的序列号。只有最后一次请求可以写入全局状态，旧请求返回时直接忽略。

这可以防止：

- 应用启动请求覆盖导入结果。
- 快速切换页面时旧请求覆盖新请求。
- 导入后当前班级状态被错误清空。

导入成功后，前端还会：

1. 重新加载班级列表。
2. 自动选择有效的当前班级。
3. 重新加载首页、学生、成绩等依赖当前班级的数据。

### 3.4 保留旧版 JSON 兼容能力

后端继续兼容旧版 `tables` 格式：

```json
{
  "app": "teacher-work",
  "version": 1,
  "tables": [
    { "table": "classes", "rows": [] },
    { "table": "students", "rows": [] }
  ]
}
```

同时支持当前 V1 交换格式：

```json
{
  "format": "teacher-work-backup",
  "formatVersion": 1,
  "content": {}
}
```

JSON 导入时会忽略附件实体文件，只恢复结构化数据；完整 ZIP 备份则同时恢复数据库和附件文件。

## 4. “从备份恢复”和“更新导入 JSON”的区别

### 从备份恢复

- 支持 ZIP 和 JSON。
- 清空当前业务数据后恢复备份内容。
- 适合在新电脑、新工作台中完整迁移。
- JSON 版本不恢复附件实体文件。
- ZIP 版本恢复数据库和附件。

### 更新导入 JSON

- 只接受 JSON。
- 不清空当前工作台。
- 将导入数据追加到当前工作台。
- 班级、学生等普通业务数据作为新的数据集导入。
- 系统默认评价分类和评价项目按唯一名称合并，避免重复数据冲突。

因此，在“全新工作台恢复原工作台”的场景中，优先使用“从备份恢复”。如果需要保留当前数据并追加旧数据，则使用“更新导入 JSON”。

## 5. 测试验证

本次新增并验证了以下关键场景。

### 5.1 真实导出 JSON → 空白工作台 → 更新导入

验证内容：

- 空工作台没有班级。
- 空工作台保留系统默认评价分类。
- 导入之前由软件导出的 JSON。
- 班级和学生能够实际查询到。
- 默认评价分类不发生唯一约束错误。
- 评价项目和关联记录外键正确。

### 5.2 真实导出 JSON → 空白工作台 → 从备份恢复

验证内容：

- 全量清空当前业务表。
- 恢复 JSON 中的全部结构化数据。
- 班级、学生、考试、成绩等记录均可查询。

### 5.3 ZIP 完整备份恢复

验证内容：

- 数据库记录恢复。
- 附件文件恢复。
- 附件哈希校验通过。
- 恢复前自动生成数据库快照。

### 5.4 前端竞态验证

验证内容：

- 启动请求晚于导入请求返回时，不覆盖导入后的班级列表。
- 导入后自动设置当前班级。
- 首页重新加载当前班级数据。

## 7. 用户验收步骤

建议使用最新便携包进行以下验收：

1. 启动全新的便携版工作台。
2. 确认当前没有班级。
3. 进入教师模式。
4. 打开“概览首页”。
5. 点击“更新导入 JSON”。
6. 选择之前从教师工作台导出的 JSON 文件。
7. 确认导入预览中的班级、学生数量。
8. 点击继续导入。
9. 确认首页出现班级名称和学生统计。
10. 切换到学生管理、成绩管理、座位管理等页面，再返回首页确认数据仍然存在。

如果需要连附件一起迁移，应改用“完整备份（含附件）”生成的 ZIP，并通过“从备份恢复”导入。

## 8. 后续防范要求

今后所有数据导入功能修改必须同时满足：

1. 测试不能只检查接口返回 200，必须查询数据库确认数据实际写入。
2. 必须测试“空白工作台导入真实导出文件”。
3. 必须测试默认种子数据存在时的导入行为。
4. 必须测试重复导入、跨版本导入和旧版格式导入。
5. 所有返回的新增数量应尽量来自实际写入结果，而不是只来自输入文件统计。
6. 任何具有唯一约束的全局配置表都必须设计明确的合并策略。
7. 导入成功后必须刷新全局状态和当前页面数据。
8. 发布前必须依次执行：

   ```text
   npm test
   npm run build
   npm run tauri:build
   npm run package:portable
   ```

本次问题表明，数据备份和恢复功能不能只看“接口是否返回成功”，必须同时验证数据库写入、外键映射、唯一约束、前端状态刷新和最终便携包内容。
