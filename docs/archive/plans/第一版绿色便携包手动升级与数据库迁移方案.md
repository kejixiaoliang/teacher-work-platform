# 教师工作台第一版绿色便携包手动升级与数据库迁移方案

> 归档说明：已被现行便携版升级与迁移文档替代，仅供历史参考。

## 1. 方案目标

教师工作台第一版采用绿色便携包交付，不使用传统安装程序，也暂不实现在线自动更新。

用户升级时只需要关闭旧程序、替换程序文件并重新启动。数据库结构升级、数据备份、迁移验证和失败保护由新版程序自动完成。

本方案的核心责任划分如下：

```text
用户负责：
关闭程序 → 替换 app/ → 重新启动

程序负责：
识别数据库版本 → 创建备份 → 执行迁移 → 验证结果 → 启动业务
```

需要达到以下目标：

- 用户不需要理解 SQLite 或手动执行 SQL；
- 更换程序文件时不覆盖真实用户数据；
- 新版程序可以读取并升级旧版数据库；
- 跨多个版本升级时，迁移可以依次执行；
- 迁移失败时不留下半升级数据库；
- 刚升级即发生故障时，可以恢复旧程序和旧数据库；
- 所有升级动作都有版本记录、备份和诊断日志。

## 2. 第一版目录结构

推荐正式绿色版固定使用以下目录结构：

```text
教师工作台/
├─ app/                         # 程序文件，可以由新版覆盖
│  ├─ 教师工作台.exe
│  └─ 其他运行文件
├─ data/                        # 用户数据，升级包不得覆盖
│  ├─ teacher.db
│  └─ files/
├─ backup/                      # 升级前备份及用户手动备份
├─ logs/                        # 启动、数据库迁移和错误日志
├─ 启动教师工作台.exe           # 可选：稳定启动器
└─ 使用说明.txt
```

目录边界必须长期保持稳定：

| 目录 | 内容 | 升级时处理方式 |
|---|---|---|
| `app/` | EXE、前端资源及运行依赖 | 可以整体替换 |
| `data/` | SQLite 数据库和用户上传文件 | 永不覆盖、永不随程序更新删除 |
| `backup/` | 升级恢复点和手动备份 | 保留 |
| `logs/` | 运行和迁移日志 | 保留，可按策略清理旧日志 |

绿色版应放在用户有写权限的位置，例如桌面、文档目录或其他数据盘。程序启动时应检查 `data/`、`backup/` 和 `logs/` 是否可写。

## 3. 发布包类型

建议每个正式版本同时提供“完整绿色包”和“纯程序升级包”，避免已有用户误覆盖数据。

### 3.1 完整绿色包

文件名示例：

```text
教师工作台-1.1.0-完整绿色版.zip
```

适用于首次使用，内容可以包括：

```text
教师工作台/
├─ app/
├─ data/          # 仅为空目录，不包含可能覆盖用户数据的数据库
├─ backup/
├─ logs/
└─ 使用说明.txt
```

如果应用能够在首次启动时自动创建 `data/`，则完整包也可以不携带该目录。

### 3.2 纯程序升级包

文件名示例：

```text
教师工作台-1.1.0-升级包.zip
```

只包含：

```text
app/
升级说明.txt
```

升级包中禁止包含：

```text
data/
backup/
logs/
teacher.db
```

即使用户使用“复制并覆盖”，升级包也只能替换程序文件，不能触碰用户数据。

## 4. 用户可见的手动升级流程

面向普通用户的升级说明应尽量简短：

```text
1. 完全关闭教师工作台。
2. 建议先在旧版中点击“完整备份”。
3. 解压新版升级包。
4. 将升级包中的 app 文件夹复制到原教师工作台目录并覆盖。
5. 不要删除、移动或覆盖 data 文件夹。
6. 重新启动教师工作台。
7. 第一次启动可能需要一些时间，程序会自动备份并升级数据库。
```

如果程序仍在运行，Windows 可能拒绝覆盖 EXE。升级说明应明确要求先退出应用，并确认后台进程已经结束。

## 5. 程序与数据库版本

程序版本和数据库结构版本是两个不同概念：

```text
程序版本：1.1.0
数据库版本：4
```

程序版本使用语义化版本号：

```text
主版本.次版本.修订版本
例如：1.3.2
```

数据库版本继续使用 SQLite：

```sql
PRAGMA user_version;
```

建议维护明确对应关系：

| 程序版本 | 需要的数据库版本 | 说明 |
|---|---:|---|
| 1.0.0 | 3 | 首个正式绿色版数据库基线 |
| 1.1.0 | 4 | 示例：新增教室名称字段 |
| 1.2.0 | 5 | 示例：调整文档分类结构 |

表中版本仅为方案示例。正式发布时应以实际程序和数据库状态确定基线。

新版启动时，应读取当前数据库版本并与自身支持范围比较：

```text
数据库版本 = 程序要求版本
→ 直接启动

数据库版本 < 程序要求版本
→ 备份并执行缺失迁移

数据库版本 > 程序支持版本
→ 禁止打开，提示程序版本过旧
```

最后一条非常重要。旧程序不能在不理解新版结构的情况下继续写入数据库。

## 6. 迁移脚本组织方式

当前项目已经通过 `PRAGMA user_version` 执行 v1、v2、v3 迁移。正式发布前，建议把迁移逐步拆分为不可修改、只能追加的独立文件：

```text
server/db/
├─ index.js                    # 打开数据库、启动迁移
├─ schema.js                   # 全新数据库的最新完整结构
├─ validate.js                 # 完整性和结构验证
└─ migrations/
   ├─ 001-initial.js
   ├─ 002-student-follow-up.js
   ├─ 003-metric-source.js
   ├─ 004-classroom-name.js
   └─ 005-document-category.js
```

每条迁移至少包含：

```text
迁移编号
迁移名称
起始数据库版本
目标数据库版本
实际变更逻辑
迁移完成后的验证逻辑
是否涉及 data/files/
是否属于破坏性迁移
```

基本规则：

1. 已经随正式版本发布的迁移脚本不能修改；
2. 后续修正只能新增更高版本迁移；
3. 全新数据库直接创建最新结构；
4. 旧数据库必须按顺序执行所有缺失迁移；
5. 不能假设用户只跨一个程序版本升级；
6. 每条迁移应尽量具备幂等保护，但不能依赖反复执行；
7. 数据库版本只能在该条迁移全部成功后更新。

## 7. 新版首次启动流程

新版第一次打开旧数据库时，推荐按以下顺序执行：

```text
定位便携版根目录
→ 检查 data/、backup/、logs/ 可写性
→ 获取程序版本
→ 检查数据库文件是否存在
→ 对现有数据库执行完整性检查
→ 读取数据库 user_version
→ 判断兼容性和所需迁移
→ 计算备份所需空间
→ 创建升级恢复点
→ 开启数据库迁移
→ 逐条执行缺失迁移
→ 验证数据库结构和关键数据
→ 提交迁移并记录目标版本
→ 执行应用启动健康检查
→ 开放业务界面
```

如果是全新用户，没有 `teacher.db`：

```text
创建最新完整数据库
→ 设置最新 user_version
→ 验证结构
→ 根据正式版策略决定是否写入示例数据
```

正式交付时应谨慎处理示例数据，避免用户删除演示内容后，在后续启动中再次自动生成。

## 8. 升级前恢复点

只要数据库版本需要变化，新版就必须先创建恢复点。建议结构如下：

```text
backup/
└─ upgrade-2026-08-04_153000-1.0.0-to-1.1.0/
   ├─ teacher.db
   ├─ files/                  # 仅在迁移涉及文件时必须复制
   └─ backup.json
```

`backup.json` 示例：

```json
{
  "type": "before-upgrade",
  "createdAt": "2026-08-04T15:30:00+08:00",
  "fromAppVersion": "1.0.0",
  "toAppVersion": "1.1.0",
  "fromDatabaseVersion": 3,
  "toDatabaseVersion": 4,
  "databaseFile": "teacher.db",
  "includesFiles": false,
  "migrationStatus": "pending"
}
```

迁移完成后可把状态改为：

```json
{
  "migrationStatus": "succeeded"
}
```

备份完成后应重新确认备份文件存在、大小合理并且能够打开，不能只判断复制操作没有抛出错误。

### 8.1 备份范围

根据迁移类型确定备份范围：

| 迁移类型 | 最低备份范围 |
|---|---|
| 仅新增普通字段 | `teacher.db` |
| 修改表结构或转换业务数据 | `teacher.db` |
| 修改文档路径、文件名或目录 | 完整 `data/` |
| 删除或合并文件数据 | 完整 `data/`，并保留操作清单 |

出于第一版实现简单和安全考虑，也可以在所有数据库迁移前统一备份完整 `data/`。缺点是上传文件较多时速度慢、占用空间大。

## 9. 数据库迁移事务

普通 SQLite 结构和数据迁移应尽量在同一事务中完成：

```sql
BEGIN IMMEDIATE;

-- 执行结构变化
-- 转换旧数据
-- 重建必要索引
-- 验证迁移结果

PRAGMA user_version = 4;

COMMIT;
```

如果任何步骤失败：

```sql
ROLLBACK;
```

只有在所有结构变化、数据转换和验证全部成功后，才能更新 `user_version` 并提交事务。

注意：文件系统操作不能由 SQLite 事务自动回滚。如果迁移同时移动 `data/files/` 中的文件，需要单独设计操作记录和补偿流程。

## 10. 常见数据库变化的处理方式

### 10.1 新增字段

新增字段通常风险较低：

```sql
ALTER TABLE classes
ADD COLUMN classroom_name TEXT DEFAULT '';
```

应确保旧记录有明确默认值，或允许字段为空。

### 10.2 新增表

新增表时还要同时考虑：

- 外键约束；
- 必要索引；
- 默认数据；
- 旧记录是否需要补充关联数据；
- 删除主记录时的级联策略。

### 10.3 修改字段含义

字段含义或枚举编码变化必须明确旧值到新值的转换规则，例如：

```text
男 → M
女 → F
空值或未知值 → U
```

转换后应统计记录数和异常值，不能静默丢弃无法识别的数据。

### 10.4 删除字段

优先分阶段停用：

```text
版本 A：停止写入旧字段
版本 B：停止读取，但继续保留字段
版本 C：确认无需回滚后，再物理删除
```

保留一个停用字段的成本通常低于立即删除带来的迁移和回滚风险。

### 10.5 重建表

SQLite 的复杂结构变化可能需要：

```text
建立新表
→ 从旧表转换并复制数据
→ 比较迁移前后记录数
→ 验证关键字段和外键
→ 删除旧表
→ 新表重命名
→ 重建索引和触发器
```

这类迁移必须使用真实旧数据库副本测试，并在升级前创建完整备份。

## 11. 迁移完成后的验证

迁移成功不能仅以“SQL 没有报错”为标准。至少应验证：

- `PRAGMA integrity_check` 结果正常；
- `PRAGMA foreign_key_check` 没有新增错误；
- 所需表和字段存在；
- 所需索引和唯一约束存在；
- 迁移前后核心表记录数符合预期；
- 必填字段没有意外空值；
- 数据转换没有未知枚举或异常数据；
- 关键查询可以执行；
- `user_version` 等于程序要求版本。

对于重要迁移，可以增加业务级验证，例如：

- 所有学生仍属于有效班级；
- 成绩仍关联有效考试和学生；
- 文档数据库记录对应的文件仍然存在；
- 座位记录没有超出班级布局范围；
- 每个唯一约束对应的数据已经完成去重处理。

## 12. 迁移失败处理

如果迁移失败，程序必须：

1. 回滚数据库事务；
2. 不更新数据库版本号；
3. 保留升级前恢复点；
4. 停止进入正常业务界面；
5. 记录详细技术日志；
6. 向用户显示简单、明确的说明；
7. 提供打开日志目录或导出诊断包的入口；
8. 提示用户恢复旧版程序或联系维护者。

用户提示示例：

```text
数据库升级没有完成。

您的原始数据已经备份，程序没有继续修改数据。
请不要重复删除或覆盖 data 文件夹。
您可以恢复旧版程序继续使用，或导出诊断信息联系维护人员。
```

程序不得在迁移失败后忽略错误继续运行。

---

## 13. 程序回滚与数据库回滚

程序文件和数据库结构存在版本对应关系：

```text
程序 1.0.0 ↔ 数据库 v3
程序 1.1.0 ↔ 数据库 v4
```

如果升级到 1.1.0 后数据库已经变成 v4，只把 `app/` 换回 1.0.0 可能造成旧程序错误读取或写坏新版数据库。

因此刚升级即失败时，应联合恢复：

```text
程序恢复为 1.0.0
+
数据库恢复为升级前 v3 备份
+
涉及文件迁移时恢复相应文件
```

旧程序启动时还应检查：

```text
当前数据库版本 > 旧程序支持的最高版本
→ 拒绝打开
→ 提示恢复匹配的程序或数据库备份
```

## 14. 升级后新增数据的回滚风险

如果用户升级后已经使用数天并录入新数据，再直接恢复升级前数据库，会丢失升级后的新增内容。

因此需要区分：

### 14.1 刚升级就失败

尚未开放业务操作，或用户尚未录入数据，可以直接恢复升级前程序和数据库。

### 14.2 使用一段时间后发现问题

不能简单覆盖数据库，应优先选择：

1. 发布修复版程序；
2. 编写向前修复迁移；
3. 导出升级后的新增数据，再恢复和合并；
4. 必要时编写经过验证的反向迁移。

因此新版完成数据库迁移后，应先执行启动健康检查和关键功能检查，再开放正常业务界面。数据库破坏性变化应尽量减少，并尽可能保持至少一个版本的向后兼容。

---

## 15. 涉及 data/files 的迁移

当前项目的用户数据不仅包括 SQLite，还包括 `data/files/` 中的上传文件。

如果新版需要改变文件名、目录或文档路径，推荐：

```text
建立完整 data/ 备份
→ 生成待迁移文件清单
→ 复制文件到新位置
→ 校验新文件大小或摘要
→ 更新数据库路径
→ 验证数据库记录与文件一致
→ 成功后再删除旧文件
```

不得先删除旧文件再尝试复制。文件操作需要保留迁移日志，使程序在断电或异常退出后能够识别已完成和未完成步骤。

---

## 16. 备份保留与空间策略

绿色版长期升级后可能产生多个恢复点。建议：

- 至少保留最近 2～3 个升级前数据库备份；
- 破坏性迁移的完整 `data/` 备份不得立即自动删除；
- 清理旧备份前必须确认当前版本运行稳定；
- 在设置中显示备份时间、程序版本、数据库版本和占用空间；
- 自动清理前提示用户，或只清理明确标记为可删除的旧备份；
- 磁盘空间不足时禁止开始迁移，不应边迁移边尝试腾空间。

上传文件较多时，完整复制 `data/` 可能占用大量空间。后续可以研究 SQLite 在线备份、硬链接、增量备份或压缩备份，但第一版优先保证方案简单和可恢复。

## 17. 日志要求

每次启动和迁移至少记录：

```text
启动时间
程序版本
数据库文件路径
迁移前数据库版本
目标数据库版本
恢复点路径
依次执行的迁移编号
每条迁移的开始和结束时间
结构及数据验证结果
最终状态
错误信息和堆栈
```

日志不得记录学生隐私明文、电话号码、成绩明细等不必要的敏感信息。

## 18. 第一版最低实现范围

正式绿色版发布前，数据库升级能力至少应完成：

- [ ] 确定首个正式数据库基线版本；
- [ ] 程序版本和数据库版本可查询；
- [ ] 迁移脚本按版本独立管理；
- [ ] 已发布迁移不可修改；
- [ ] 支持跨多个数据库版本顺序升级；
- [ ] 迁移前自动备份数据库；
- [ ] 涉及文件变化时备份完整 `data/`；
- [ ] 数据库迁移在事务内执行；
- [ ] 迁移后进行完整性、外键和结构验证；
- [ ] 迁移失败时禁止进入业务页面；
- [ ] 旧程序拒绝打开过新的数据库；
- [ ] 提供打开数据目录和备份目录的入口；
- [ ] 提供完整备份和恢复能力；
- [ ] 完整绿色包与纯程序升级包分开发布；
- [ ] 升级包不包含 `data/`；
- [ ] 提供面向普通用户的升级说明；
- [ ] 记录可导出的迁移日志。

## 19. 发布前测试矩阵

每个涉及数据库变化的版本至少测试：

| 场景 | 预期结果 |
|---|---|
| 全新目录首次启动 | 创建最新数据库并正常运行 |
| 当前数据库无需迁移 | 不产生重复结构和重复数据 |
| 从上一个版本升级 | 自动备份并升级成功 |
| 跨两个或更多版本升级 | 所有缺失迁移按顺序执行 |
| 数据库为空但结构较旧 | 正确升级，不错误写入演示数据 |
| 数据库包含大量业务数据 | 记录数和关键关联保持正确 |
| 数据库文件损坏 | 停止迁移并提示恢复 |
| 数据目录只读 | 启动前阻止写入并明确提示 |
| 备份空间不足 | 不开始迁移 |
| 某条 SQL 故意失败 | 整体回滚，版本号不变 |
| 迁移过程中程序异常退出 | 原库或备份可以恢复 |
| 新版打开更高版本数据库 | 拒绝打开并说明原因 |
| 旧版打开已迁移数据库 | 拒绝写入，避免数据损坏 |
| 涉及上传文件迁移 | 数据库记录与实际文件一致 |
| 刚升级后执行联合回滚 | 旧程序和旧数据库正常匹配 |

建议为每一个已经正式发布的数据库版本保存一份脱敏测试数据库，以便后续版本持续测试：

```text
tests/fixtures/databases/
├─ schema-v3-sample.db
├─ schema-v4-sample.db
└─ schema-v5-sample.db
```

测试数据库不得包含真实学生隐私数据。

## 20. 当前项目下一步建议

在实际制作第一版 Tauri 绿色包之前，建议按以下顺序落实：

1. 盘点当前 `server/db.js` 中的完整表结构和 v1～v3 迁移；
2. 确定首个正式版数据库基线；
3. 将数据库初始化、迁移、验证和备份职责分离；
4. 建立旧版本脱敏数据库样本；
5. 实现迁移前备份和迁移后验证；
6. 实现数据库版本过高保护；
7. 固定绿色版 `app/`、`data/`、`backup/` 和 `logs/` 边界；
8. 构建完整包和纯程序升级包；
9. 使用真实升级流程进行人工与自动化测试；
10. 确认第一版稳定后，再讨论离线升级助手或在线更新。

## 21. 最终结论

第一版采用手动绿色升级时，用户只负责替换程序，数据库不能要求用户手动处理。

完整升级模型应是：

```text
手动替换程序
→ 新版自动识别旧数据库
→ 自动创建恢复点
→ 自动按版本执行迁移
→ 自动验证迁移结果
→ 成功后开放使用
→ 失败时保持或恢复旧数据
```

只要坚持以下原则，数据库结构可以在后续版本中持续演进：

1. 升级包永不覆盖 `data/`；
2. 数据库变化必须通过顺序化迁移完成；
3. 迁移前必须备份；
4. 迁移完成后必须验证；
5. 失败时程序和数据库必须能够联合恢复；
6. 已经使用一段时间的新版数据库不能简单用旧备份覆盖；
7. 每个正式数据库版本都必须进入长期升级测试矩阵。
