# 教师工作台 v0.8.0 客户端到小程序迁移流程与微信身份资料确认设计说明

> 建立日期：2026-08-28  
> 文档类型：设计说明与执行流程  
> 适用范围：以桌面客户端为业务基准，重新实现微信小程序  
> 当前分支：仅作历史归档和资产来源，禁止合并到 `main`

## 1. 总体结论

客户端是业务、数据和功能的唯一基准；小程序是同一套业务模型的移动端实现。两端可以使用不同的页面、导航、交互和本地技术，但数据字段、稳定 UUID、状态枚举、权限规则、导入导出格式和业务语义必须统一。

迁移不应采用“先把所有客户端页面翻译成小程序，最后一次性验收”的方式。正确流程是：

```text
客户端总体审查
  → 冻结业务与数据基线
  → 建立历史数据样本和契约测试
  → 小程序运行时冒烟
  → 一条核心业务纵向闭环
  → 微信端真实验收
  → 按模块逐个迁移
  → 跨端数据对照和发布
```

## 2. 第一阶段：客户端基线审查

### 2.1 审查对象

以一个稳定客户端版本作为黄金基线，例如 v0.7.0。审查范围包括：

- 所有模块、页面、路由、快捷入口和空状态入口。
- 所有按钮、菜单、批量操作、导入导出和恢复操作。
- SQLite 表、字段、索引、外键、迁移版本和附件目录。
- Express/Tauri 接口、请求参数、返回值和写入副作用。
- 教师模式、班级公开模式、敏感数据和安全设置。
- 加载中、空数据、无权限、网络失败、部分成功和回滚失败状态。
- 颜色、字体、间距、信息层级和常用操作的 UI 基线。

### 2.2 必须形成的审查资料

1. 模块与入口地图。
2. 功能能力矩阵：查看、新增、编辑、删除、批量、导入、导出、恢复、打印。
3. 按钮行为表：前置条件、接口、数据副作用、成功刷新和失败提示。
4. 数据字典：字段、类型、默认值、枚举、关系和稳定 ID。
5. 接口与权限登记表。
6. 数据兼容矩阵：旧数据库、旧 JSON、旧 ZIP、Excel 模板。
7. UI 设计基线和移动端改编约束。
8. 脱敏样本目录及预期结果。

这些资料描述的是业务行为，不是把 Vue 组件或桌面页面代码复制一遍。

## 3. 第二阶段：冻结数据与兼容契约

### 3.1 统一数据规则

- 客户端、小程序和云端使用同一套字段、状态和关联关系。
- 跨端记录使用稳定 UUID，不使用 SQLite 数字 ID 或 CloudBase `_id` 作为跨端主键。
- 新客户端和新小程序必须导入旧版本已经承诺支持的数据。
- 新版本只导出最新格式，但永久保留旧格式迁移器。
- 软件版本、SQLite `user_version`、JSON `formatVersion` 和 ZIP 版本独立维护。
- 字段新增、删除、重命名和语义变化必须通过迁移器处理。
- 旧数据缺失字段时使用明确默认值，不把缺失成绩变成 `0`，不伪造日期。

### 3.2 统一导入链路

所有 JSON、ZIP 和模块文件都必须遵循：

```text
识别格式 → 历史迁移 → 统一模型 → 校验 → 预览 → 提交 → 报告
```

恢复和更新导入必须区分：

- 恢复整个工作台：替换语义，必须创建快照并支持回滚。
- 更新导入：不清空现有数据，默认导入为新数据集或新班级。

## 4. 第三阶段：建立测试和证据基线

至少准备：

- 空数据库和空数据集。
- 一个班级、多个班级、学生及其关联业务数据。
- v0.7、v0.6、v0.5 等历史 JSON/ZIP 脱敏样本。
- 缺字段、旧字段、重复记录、损坏文件和缺附件样本。
- 真实业务操作的预期记录数、字段值和 UUID 对照表。

自动化测试和真实平台验收必须分开记录：

| 级别 | 证据 | 结论 |
| --- | --- | --- |
| L0 | 文件和静态检查 | 工程文件已准备 |
| L1 | 单元/契约测试 | 逻辑契约通过 |
| L2 | 微信目标平台编译 | 目标平台可编译 |
| L3 | 模拟器真实点击 | 页面基本可用 |
| L4 | 脱敏微信身份读写 | 业务闭环可用 |
| L5 | 真机、多尺寸、历史数据、恢复回滚 | 可以进入发布评估 |

没有达到 L2，不得说“可以使用”；没有达到 L4，不得说“业务闭环完成”。

## 5. 第四阶段：小程序运行时冒烟

第一批只实现三个入口：

```text
启动页 → 身份/环境检查 → 数据集和班级列表
```

必须先确认：

- 微信开发者工具打开的是小程序项目根目录，而不是父目录或 `miniprogram/` 子目录。
- JS、WXML、WXSS 都能编译。
- 首屏能渲染，底部导航和页面跳转正常。
- CloudBase 环境未配置时显示明确错误，不静默显示“已登录”。
- 使用脱敏数据能读取一个班级和学生列表。

运行时冒烟不过，禁止继续增加几十个业务页面。

## 6. 第五阶段：先完成一条纵向业务闭环

推荐以学生管理为第一条闭环：

```text
微信身份
  → 数据集选择
  → 班级选择
  → 学生列表
  → 学生详情
  → 新增/编辑
  → 软删除
  → 客户端按同一 UUID 读取
```

这条链必须同时通过自动化测试、微信开发者工具模拟器和脱敏微信身份验证，才允许迁移第二个模块。

## 7. 第六阶段：按模块逐个迁移

每个模块固定执行：

1. 对照客户端功能矩阵和字段。
2. 设计小程序服务层契约，不在页面中直接拼接权限和云函数细节。
3. 实现查看、写入、删除、导入导出等完整动作，不只做展示页。
4. 实现加载、空、错误、无权限、部分成功和重试状态。
5. 添加契约、集成和历史数据回归测试。
6. 在模拟器和真实设备尺寸中点击验收。
7. 将小程序产生的数据导回客户端，验证字段、状态和 UUID。
8. 记录已验证范围、未完成动作和已知限制。

桌面 UI 只提供视觉和信息层级基线；小程序应重新设计触达尺寸、滚动、分步表单、批量操作和文件交互，不能机械照搬桌面布局。

## 8. 微信身份与用户资料确认设计

### 8.1 两个概念必须分开

**微信身份登录**：微信小程序通过原生 `wx.cloud` 体系自动建立当前用户身份，云函数从上下文取得身份。它不等于账号密码登录，也不需要伪造一个 Web 登录页。

**用户资料确认**：头像和昵称属于用户主动提供的资料，应通过明确的交互让用户选择或填写。不能把“身份状态检查”冒充成完整登录体验。

### 8.2 首次使用流程

```text
小程序启动
  → 检查微信身份和 CloudBase 环境
  → 查询当前教师资料
  → 未完善资料：显示首次使用确认页
  → 用户点击选择头像
  → 用户填写/选择昵称
  → 用户阅读并同意隐私说明
  → 点击“确认并进入工作台”
  → 云函数按当前微信身份保存教师资料
  → 进入首页
```

### 8.3 页面控件要求

- 头像使用 `button open-type="chooseAvatar"`，通过 `bindchooseavatar` 获取用户主动选择的临时路径。
- 昵称使用 `input type="nickname"`，通过输入事件取得用户确认的值。
- 提供清晰的“确认并进入工作台”按钮。
- 提供“稍后完善”策略时，必须明确哪些功能会受限；敏感数据功能不能在未同意隐私说明时开放。
- 再次进入时显示已保存的头像和昵称，并在设置中提供修改入口。

### 8.4 数据和安全要求

- 教师资料保存到 `teacher_profiles` 或等价集合。
- 云函数根据当前微信上下文写入，不能信任客户端传入的 `openid` 或 `ownerId`。
- 头像临时文件如需跨设备显示，应先上传到 CloudBase 存储，再保存稳定文件引用。
- 页面不展示 OPENID，不把身份标识写入剪贴板或分享内容。
- `identity-status` 只负责认证状态检查，不能承担用户资料登录页面职责。
- 不重新引入依赖账号密码的 Web 登录体系。

## 9. 高风险能力的迁移顺序

完整备份、Excel 文件、恢复、同步和电脑端绑定必须晚于基础闭环，并分别具备：

- 脱敏测试数据集。
- 预检和预览。
- 二次确认。
- 快照、回滚和幂等。
- 失败报告和审计记录。
- 微信身份下的真实点击证据。

“同步状态检查”不能称为双向同步；真正同步还需要变更队列、游标、冲突、重试和可恢复状态。

## 10. 明确禁止的做法

- 不先验证启动和导航，就批量创建业务页面。
- 不把页面文件齐全、测试通过或云函数 `AUTH_REQUIRED` 冒烟当成真实可用。
- 不直接复制桌面页面和数据库内部结构。
- 不为了小程序创建另一套业务 ID、字段或状态。
- 不在真实生产数据上反复调试导入、恢复和同步。
- 不修改已发布的迁移脚本。
- 不把当前实验分支合并到 `main`。

## 11. 发布前最终检查

- 客户端基线版本、数据契约和历史兼容矩阵已冻结。
- 新客户端/小程序能够导入旧版本已承诺数据。
- 运行时达到至少 L4 证据级别。
- 身份、头像、昵称和隐私确认流程可完成。
- 至少一个真实业务闭环可以在客户端和小程序之间互相核对。
- 高风险操作都有预览、确认、快照和回滚记录。
- 未完成范围已经在发布说明中明确列出。

## 12. 最终原则

> 先把客户端业务和数据讲清楚，再让小程序实现同一套契约；先让用户真实完成一件工作，再扩展下一件；先证明数据不丢，再讨论页面是否漂亮。
