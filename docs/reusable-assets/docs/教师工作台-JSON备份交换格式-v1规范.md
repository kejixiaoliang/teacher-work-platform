# 教师工作台 JSON 备份交换格式 v1 规范

> 文档状态：设计规范  
> 适用范围：本地教师工作台、未来微信小程序、云端导入服务  
> 当前目标版本：v0.7.0 及后续版本  
> 创建日期：2026-08-25

## 1. 设计目标

本规范用于定义教师工作台的纯 JSON 备份文件格式，使本地版导出的数据可以在未来的小程序或云端服务中导入，并保证新版本能够继续读取旧版本导出的文件。

本规范解决以下问题：

- 本地业务数据如何导出为稳定的 JSON 文件
- JSON 文件如何标识格式版本和来源版本
- 如何检查文件是否损坏或传输不完整
- 如何在不导入附件的前提下保留业务记录
- 如何避免本地自增 ID 与云端 ID 冲突
- 新版本如何兼容旧版本导出的文件
- 云端导入失败时如何避免产生半成品数据

本规范第一版明确采用“JSON 数据、不导入附件”的策略。附件可以在未来单独设计，但不能阻塞当前 JSON 数据的迁移和恢复。

## 2. 非目标

v1 不负责：

- 导出或导入图片、文档、音频等附件内容
- 多端实时同步
- 已有云端数据与备份数据的复杂合并
- 云端账号体系设计
- 云端文件存储协议
- 对备份文件进行数字签名

SHA256 在 v1 中只用于完整性校验，不用于证明文件来源或防止恶意伪造。

## 3. 文件格式总览

备份文件是 UTF-8 编码的 JSON 文本文件，建议文件扩展名为 `.teacher-work.json`。

顶层结构如下：

```json
{
  "format": "teacher-work-backup",
  "formatVersion": 1,
  "appVersion": "0.6.0",
  "databaseVersion": 6,
  "exportId": "3f9f2b6e-3c1d-4d9e-9d6b-55a4f4d2c9f7",
  "exportedAt": "2026-08-25T12:00:00.000Z",
  "source": {
    "platform": "desktop",
    "product": "teacher-work",
    "timezone": "Asia/Shanghai"
  },
  "content": {
    "classes": [],
    "students": [],
    "attendance": [],
    "assessment": [],
    "scores": [],
    "leaves": [],
    "contacts": [],
    "followUpTasks": [],
    "documents": [],
    "settings": {}
  },
  "attachments": {
    "included": false,
    "omittedCount": 0
  },
  "integrity": {
    "algorithm": "sha256",
    "scope": "canonical-json-without-integrity-value",
    "value": ""
  }
}
```

## 4. 顶层字段规范

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `format` | string | 是 | 固定值 `teacher-work-backup` |
| `formatVersion` | integer | 是 | JSON 交换格式版本，v1 为 `1` |
| `appVersion` | string | 是 | 导出数据的软件版本，例如 `0.6.0` |
| `databaseVersion` | integer | 是 | 导出时本地数据库结构版本 |
| `exportId` | UUID string | 是 | 本次导出的唯一标识 |
| `exportedAt` | ISO 8601 string | 是 | 导出时间，统一使用 UTC 或带时区时间 |
| `source` | object | 是 | 导出来源信息 |
| `content` | object | 是 | 业务数据主体 |
| `attachments` | object | 是 | 附件是否包含的说明 |
| `integrity` | object | 是 | 文件完整性校验信息 |

### 4.1 `format`

固定为：

```text
teacher-work-backup
```

导入器必须先检查该字段。格式不匹配时不得尝试猜测文件类型。

### 4.2 `formatVersion`

`formatVersion` 表示交换协议版本，而不是软件版本。

软件版本升级不一定导致格式版本升级。只有发生以下变化时才升级格式版本：

- 顶层结构发生不兼容变化
- 关键字段语义发生变化
- 数据关联方式发生变化
- 旧版本无法通过迁移器转换为新内部结构

### 4.3 `appVersion` 与 `databaseVersion`

这两个字段用于诊断和迁移判断，但不能单独决定导入逻辑。

导入顺序必须是：

```text
先按 formatVersion 选择格式迁移器
再根据 databaseVersion 补充数据库字段兼容处理
```

### 4.4 `exportId`

每次导出都必须生成新的 UUID。它用于：

- 标识一次导出任务
- 防止同一个备份重复导入
- 记录云端导入日志
- 在导入失败时定位问题

## 5. 业务数据结构

### 5.1 数据集合原则

`content` 中的集合必须使用数组，即使集合为空也必须输出空数组：

```json
{
  "classes": [],
  "students": [],
  "attendance": []
}
```

不得因为数据为空而省略字段。这样可以避免不同版本对缺失字段产生歧义。

### 5.2 稳定 UUID

每条可以被其他记录引用的业务数据都必须有稳定 UUID。建议保留本地数字 ID 作为诊断字段，但不能使用本地数字 ID 作为跨设备身份。

示例：

```json
{
  "id": 12,
  "uuid": "1b4e28ba-2fa1-11d2-883f-0016d3cca427",
  "name": "张三",
  "classUuid": "8a1f52e2-a9c8-4cf1-9c1c-86db05f9a4c1"
}
```

约束：

- `uuid` 在同一数据类型内必须唯一
- UUID 在导出、导入和后续再次导出时保持不变
- 云端主键可以使用自己的 ID，但必须保存来源 UUID
- 关系字段优先使用 `classUuid`、`studentUuid` 等稳定引用
- 不允许只依赖数组顺序或本地自增 ID 建立关系

### 5.3 推荐业务集合

v1 推荐包含以下集合：

- `classes`：班级
- `students`：学生基本信息
- `attendance`：考勤记录
- `assessment`：表现量化规则、分类、记录和修订信息
- `scores`：成绩及考试信息
- `leaves`：请假记录
- `contacts`：家校沟通记录
- `followUpTasks`：学生跟进事项
- `documents`：文档元数据，不包含文件内容
- `settings`：与业务恢复相关的非敏感配置

### 5.4 敏感信息禁止导出

以下内容不得进入 JSON 备份：

- 教师密码摘要
- 密码盐
- 教师会话 Token
- API Token
- 恢复密钥原文
- 云端访问 Token
- 本地文件绝对路径
- 操作系统用户名
- 运行时临时目录

可以导出业务上的隐私记录，例如家校沟通和学生跟进，但导入过程必须经过教师身份验证。

## 6. 附件不导入策略

v1 不包含附件内容，但必须明确记录附件被省略：

```json
{
  "attachments": {
    "included": false,
    "omittedCount": 12
  }
}
```

对于带有附件关联的业务记录：

- 保留文字、日期、类型和业务关联
- 保留附件展示名称（如果存在）
- 不保留本地绝对路径
- 将附件状态标记为 `omitted` 或由导入器生成缺失提示
- 不因为附件缺失而拒绝整份 JSON 导入

示例：

```json
{
  "uuid": "4d6d3c1a-94f0-49ef-8c31-4d5d0b7f8a88",
  "studentUuid": "1b4e28ba-2fa1-11d2-883f-0016d3cca427",
  "name": "家长沟通记录",
  "attachment": {
    "included": false,
    "originalName": "沟通记录.pdf",
    "status": "omitted"
  }
}
```

## 7. 完整性校验

### 7.1 校验算法

v1 使用 SHA256：

```text
algorithm = sha256
scope = canonical-json-without-integrity-value
```

计算步骤：

1. 复制完整 JSON 对象
2. 将 `integrity.value` 设置为空字符串
3. 按规范化 JSON 规则序列化
4. 使用 UTF-8 字节计算 SHA256
5. 将十六进制小写结果写入 `integrity.value`

### 7.2 规范化 JSON

为了保证不同语言生成的校验值一致，序列化规则固定为：

- 对象键按 Unicode 字典序递归排序
- 数组保持业务顺序，不排序
- 使用 UTF-8
- 不输出额外空格和换行
- 使用 JSON 标准字符串转义
- 数字不得使用 `NaN`、`Infinity` 或未定义值
- 时间统一使用 ISO 8601 字符串

伪代码：

```js
function canonicalize(value) {
  if (Array.isArray(value)) return `[${value.map(canonicalize).join(',')}]`;
  if (value && typeof value === 'object') {
    return `{${Object.keys(value).sort().map(key =>
      `${JSON.stringify(key)}:${canonicalize(value[key])}`
    ).join(',')}}`;
  }
  return JSON.stringify(value);
}
```

### 7.3 导入时校验失败处理

以下情况必须拒绝导入：

- `format` 不正确
- `formatVersion` 缺失或不支持
- `integrity` 缺失
- SHA256 不匹配
- JSON 无法解析
- 必填集合不是数组
- UUID 重复或引用关系无法解析

错误信息应该说明问题，但不能输出密码、Token 或完整敏感数据。

## 8. 版本兼容策略

### 8.1 迁移器模型

每个格式版本都由明确的迁移器负责转换：

```text
v1 JSON ──normalizeV1()──┐
v2 JSON ──normalizeV2()──┼──> 当前统一内部模型 ──> 云端导入
v3 JSON ──normalizeV3()──┘
```

导入器不得把 JSON 直接映射到数据库表。必须先转换到统一内部模型。

### 8.2 向后兼容

每个新版本至少保证：

- 可以导入当前版本生成的文件
- 可以导入前两个格式版本生成的文件
- 对更老版本，如果仍保留迁移器则继续支持
- 不支持的格式版本给出明确错误，不静默丢弃数据

### 8.3 缺少字段

旧版本缺少新字段时使用明确默认值：

```js
const student = {
  uuid: input.uuid,
  name: input.name || '',
  status: input.status || '在读',
  gradeLevel: input.gradeLevel ?? '',
};
```

不得把缺失字段默认为可能造成数据误解的值。例如缺少成绩不能默认填 `0`，应使用 `null` 或空值。

### 8.4 字段重命名和废弃

字段重命名必须在迁移器中处理：

```js
const title = input.title ?? input.taskTitle ?? '';
```

废弃字段在至少两个格式版本内继续读取；导出新版本时可以不再写出，但不得因为旧字段存在而失败。

### 8.5 格式版本升级规则

以下变化可以继续使用相同 `formatVersion`：

- 新增可选字段
- 新增非关键业务集合
- 增加诊断信息

以下变化必须升级 `formatVersion`：

- 删除必填字段
- 改变字段含义
- 改变 UUID 或关系字段语义
- 改变校验算法或规范化规则
- 旧版无法无损转换

## 9. 导入流程

未来小程序或云端导入服务必须采用分阶段导入：

```text
上传 JSON
  ↓
解析与格式检查
  ↓
SHA256 校验
  ↓
版本迁移
  ↓
数据完整性检查
  ↓
生成导入预览
  ↓
教师确认
  ↓
事务性写入云端
  ↓
刷新小程序数据
```

### 9.1 导入预览

正式写入前应显示：

- 导出软件版本
- JSON 格式版本
- 导出时间
- 班级数量
- 学生数量
- 考勤记录数量
- 量化记录数量
- 成绩记录数量
- 家校沟通和跟进事项数量
- 被省略的附件数量
- 是否检测到重复 UUID

第一版建议只支持“导入为新数据集”，不直接合并已有云端数据。

### 9.2 事务和回滚

导入必须具备以下行为：

- 预检失败时不写入业务数据
- 正式导入前创建云端导入任务记录
- 所有核心业务数据在同一导入事务或可回滚批次中写入
- 中途失败时标记任务失败并清理半成品
- 导入成功后记录 `exportId`
- 同一个 `exportId` 默认不能重复导入

### 9.3 重复导入策略

v1 默认拒绝同一 `exportId` 的重复导入：

```text
该备份文件已经导入过，是否创建新的数据集？
```

如果教师明确选择重新导入，应创建新的数据集，而不是覆盖原数据。复杂合并和覆盖策略放到后续版本。

## 10. 云端数据集模型

未来云端不应把所有数据直接混在一个全局空间中，建议引入数据集概念：

```text
用户账号
  └─ 数据集 / 班级空间
       ├─ 班级
       ├─ 学生
       ├─ 考勤
       ├─ 成绩
       └─ 跟进记录
```

导入时创建：

- `datasetId`
- `sourceExportId`
- `sourceAppVersion`
- `sourceFormatVersion`
- `importedAt`
- `importStatus`

所有业务记录保存来源 UUID，便于后续同步和诊断。

## 11. 安全要求

JSON 备份可能包含成绩、学生隐私和家校沟通内容，必须视为敏感文件处理。

要求：

- 导出前给出敏感数据提示
- 导入接口必须要求教师身份认证
- 上传文件使用 HTTPS
- 云函数不把完整 JSON 写入普通日志
- 导入完成后删除临时上传文件
- 错误日志只记录 `exportId` 和错误类型
- 不在前端 LocalStorage 保存教师密码或恢复密钥
- 恢复密钥不能进入 JSON 备份
- 云端导入任务应绑定当前用户和数据集

## 12. 测试要求

### 12.1 导出测试

- 空数据集可以导出
- 多班级、多学生数据可以导出
- 所有集合字段始终存在
- UUID 在同类数据中唯一
- 不包含密码、Token、恢复密钥和本地绝对路径
- 附件被正确标记为未包含

### 12.2 校验测试

- 正确 JSON 校验通过
- 修改一个字符后校验失败
- 缺失 `integrity` 时拒绝
- 不支持的算法时拒绝
- 键顺序变化不会改变规范化后的校验结果

### 12.3 兼容测试

- v1 文件可以被当前版本导入
- 旧文件缺少新增字段时使用正确默认值
- 旧字段名称可以迁移到新字段
- 不支持的版本不会静默导入
- 导入后再次导出，核心业务数据保持一致

### 12.4 导入测试

- 导入预览数量正确
- 重复 `exportId` 被识别
- 重复 UUID 被识别
- 关系字段可以正确重建
- 导入中途失败不会留下半成品
- 不带附件仍然可以完成业务数据导入

## 13. 实施建议

建议分三个阶段实现：

### 阶段一：本地 JSON 导出

- 定义 v1 JSON 结构
- 为现有数据补充稳定 UUID
- 实现规范化 JSON 和 SHA256
- 导出班级、学生、考勤、量化、成绩和跟进数据
- 明确不导入附件

### 阶段二：本地 JSON 导入

- 实现 v1 解析器
- 实现版本检查和完整性校验
- 实现导入预览
- 支持导入到本地新数据集
- 增加导入回滚和重复导入测试

### 阶段三：小程序云端导入

- 小程序上传 JSON
- 云函数执行校验和迁移
- 云端创建数据集
- 云端写入业务数据
- 小程序刷新并加载云端数据
- 增加云端导入日志和失败重试

## 14. 最终原则

本规范最终遵循以下原则：

1. JSON 是业务交换格式，不是数据库文件复制。
2. `formatVersion` 决定迁移方式，不能只看软件版本。
3. 所有跨设备关系使用稳定 UUID，不依赖本地自增 ID。
4. SHA256 用于发现文件损坏，不代表身份认证。
5. 附件不导入，但必须明确记录被省略。
6. 旧版本文件必须由新版本迁移器负责兼容。
7. 导入前必须校验和预览，导入过程必须可回滚。
8. 第一版优先支持导入为新数据集，不直接做复杂合并。
9. 备份文件包含敏感数据，导出、传输和导入都必须受保护。
10. 每次格式升级都必须增加对应的兼容测试样本。
