## 一、核心目标

在不破坏 v0.7.0 及历史版本数据的前提下，为电脑端、小程序端和 CloudBase 云端建立永久兼容的数据基础。

本阶段最高优先级不是增加页面，而是保证以下链路长期可用：

```text
旧版客户端数据库 / 旧版 JSON / ZIP 导出
        ↓
历史格式识别与迁移
        ↓
统一内部数据模型
        ↓
CloudBase 云端数据
        ↑
电脑端同步 / 小程序读取和写入
```

## 二、版本基线和版本职责

| 版本类型 | 当前值 | 职责 |
| --- | ---: | --- |
| 软件版本 | v0.7.0 | 当前发布的软件功能版本 |
| SQLite 数据库版本 | 7 | 本地数据库结构迁移版本 |
| JSON 交换格式版本 | 1 | 跨端 JSON 协议版本 |
| 完整 ZIP 归档版本 | 2 | 本地数据库和附件归档格式 |
| 单模块导出格式版本 | 模块自有 | 例如表现量化专项导出格式 |

规则：软件版本升级不自动导致数据格式升级；SQLite、JSON 和 ZIP 版本独立维护；每种格式都必须有自己的读取、迁移和测试策略。

## 三、现有项目审查结论

### 3.1 已有基础

- `package.json`、Tauri 配置和更新日志当前已进入 v0.7.0。
- SQLite `DATABASE_VERSION` 当前为 7，并按 `user_version` 逐级迁移。
- 数据库升级前会创建恢复快照。
- 已有 `record_uuids` 表。
- 当前 JSON 交换格式为 `teacher-work-backup`，`formatVersion = 1`。
- JSON 已包含导出标识、来源信息、附件省略信息和 SHA-256 完整性校验。
- 当前支持旧版 `tables` JSON 的版本 1/2 兼容导入。
- 当前完整 ZIP 归档使用独立版本并包含附件文件。
- JSON 导出不包含附件内容，适合未来小程序结构化数据导入。
- 已有备份、迁移、交换格式、完整性校验和学生 Excel 导入测试。

### 3.2 必须优先处理的问题

#### UUID 生成策略

当前 UUID 由数据表名称和本地整数 ID 推导，适合单个本地数据库内的稳定交换，但多个数据库合并时存在潜在冲突。

v0.8.0 必须改为：新记录创建时生成随机 UUID，旧记录已有 UUID 时永久保持，旧记录没有 UUID 时只生成一次并写入映射表。禁止因为升级 UUID 方案而重新生成历史 UUID。

#### 云端归属字段

本地数据没有教师身份字段。导入 CloudBase 时必须由当前认证身份写入 `ownerId`，不能信任导入文件自行提供的所有者字段。

#### 同步元数据

当前业务表没有统一的云端版本、删除时间、同步状态和冲突信息。需要补充 `revision`、`deletedAt`、同步游标和本地同步队列。

#### 本地备份和云端导入边界

现有 JSON 适合结构化数据交换，ZIP 适合本地数据库和附件恢复。小程序第一期只接收 JSON，不把 ZIP 中的附件恢复到云端。

## 四、永久兼容规则

### 4.1 兼容方向

```text
新版本只导出最新规范
新版本永久保留旧版本导入器
历史格式文件只读，不被覆盖或改写
```

软件版本从 v0.7.0 升级到 v0.8.0 时，仍应继续支持 v0.7.0 以及已承诺支持的历史 JSON/ZIP 文件。

### 4.2 历史格式支持矩阵

| 来源格式 | 当前情况 | v0.8.0 要求 |
| --- | --- | --- |
| v0.7.0 `teacher-work-backup` JSON | 当前格式 v1 | 必须支持 |
| v0.6.0 及更早新版 JSON | 可能使用交换格式 v1 | 通过 v1 规范读取 |
| 旧版 `tables` JSON v1/v2 | 当前已兼容 | 保留读取器 |
| v0.4.2 及更早完整 ZIP | 含数据库和附件 | 电脑端继续恢复；云端只取结构化数据 |
| 学生 Excel | 人工录入格式 | 保留电脑端导入，不作为同步格式 |
| 表现量化专项 JSON | 模块格式 | 保留专项读取器 |

### 4.3 迁移器模型

```text
legacy tables v1/v2 ─┐
teacher-work-backup v1 ─┼─> normalize() ─> unified records ─> validate() ─> persist()
full ZIP v2 ──────────┘
```

迁移器必须明确返回来源版本、来源导出 ID、规范化数据、警告和错误。外部输入不得直接拼接到 SQLite 或 CloudBase 写入请求。

### 4.4 字段兼容

- 新增字段使用明确且安全的默认值。
- 删除字段时旧字段可以读取后丢弃，但不能阻止导入。
- 重命名字段由迁移器同时读取旧名称和新名称，并规定优先级。
- 改变字段语义时必须升级 `formatVersion`。
- 缺少成绩使用 `null` 或空值，不能默认变成 `0`。
- 缺少日期使用空值并在报告中提示，不能伪造当前日期。
- 日期、布尔值、数字和 JSON 字段使用统一规范化函数。

## 五、统一数据模型

### 5.1 记录标识

```text
uuid          # 永久稳定的来源记录标识
cloudId       # CloudBase 文档 _id，可选
ownerId       # 教师身份
createdAt
updatedAt
deletedAt
revision      # 云端版本
source        # desktop / miniprogram / import
```

本地 SQLite `id` 保留为 `legacyId` 或诊断字段，不作为跨端主键。

### 5.2 关系字段

跨端关系优先使用 UUID：

```text
classUuid
studentUuid
examUuid
itemUuid
recordUuid
```

迁移时先建立父记录 UUID，再转换子记录引用。无法解析父记录时拒绝该子记录并输出错误。

### 5.3 教师数据隔离

云端所有业务记录必须有 `ownerId`。服务端从当前认证身份取得 `ownerId`，不信任客户端传入的所有者字段。

第一期虽然只有教师本人使用，也按多教师隔离设计，避免未来重新改表。

## 六、CloudBase 迁移方案

### 6.0 微信开发者工具项目根目录与云函数目录

本项目不是把小程序单独放到另一个仓库，而是在现有桌面端仓库内新增微信小程序工程。微信开发者工具应打开整个仓库根目录：

```text
E:\CodeFile\MyAIProject\Reasonix-test\teacher-work
```

根目录新增 `project.config.json`，至少明确：

```json
{
  "miniprogramRoot": "miniprogram/",
  "cloudfunctionRoot": "cloudfunctions/"
}
```

目录职责固定如下：

- `miniprogram/`：小程序页面、组件、服务和资源；
- `cloudfunctions/`：实际部署到 CloudBase 的云函数，每个函数一个子目录；
- `cloudbase/`：数据库集合、索引、权限、迁移和云托管/静态托管文档，不作为实际云函数根目录；
- `shared/`：以后存放跨端数据契约、枚举、交换格式和校验规则；
- `web/`、`server/`、`src-tauri/`：现有电脑端目录，保持原位置不动。

因此，之前把函数写成 `cloudbase/functions/` 的规划应统一修正为根目录 `cloudfunctions/`。这只是工程组织和开发者工具识别方式的修正，不改变 CloudBase 的云端数据架构。

### 6.1 云端数据分层

```text
teachers
  └─ datasets
       └─ classes / students / attendance / scores / records ...
```

每次本地导入云端都创建导入批次和来源记录：

```text
import_batches
- importBatchId
- ownerId
- sourceExportId
- sourceAppVersion
- sourceFormatVersion
- status
- createdAt
- completedAt

datasets
- datasetId
- ownerId
- sourceImportBatchId
- name
- status
- createdAt
```

业务集合保留 `datasetId` 和来源 `uuid`，便于同步、审计和问题定位。

### 6.2 导入流程

```text
选择 JSON
  ↓ 格式识别
  ↓ 完整性校验
  ↓ 历史版本迁移
  ↓ 字段和关系校验
  ↓ 生成预览报告
  ↓ 教师确认
  ↓ 创建导入批次
  ↓ 分批幂等写入
  ↓ 校验数量和关系
  ↓ 提交成功或回滚
```

### 6.3 默认导入策略

第一期默认“导入为新数据集”，不直接覆盖当前云端数据，也不自动合并同名班级。

重复导入同一 `exportId` 时：

- 成功过的导入提示已完成；
- 失败过的导入允许重试或清理；
- 用户明确选择重新导入时创建新的批次和数据集。

复杂合并、覆盖和双向冲突解决不在第一期隐式执行。

## 七、电脑端和小程序同步边界

### 7.1 电脑端

- SQLite 继续作为离线缓存和本地工作副本。
- 本地写入后进入同步队列。
- 联网后向 CloudBase 上传变更。
- 从 CloudBase 按游标下载变更。
- 本地附件第一期不上传。

### 7.2 小程序

- 直接访问 CloudBase 云端业务数据。
- 使用微信身份识别教师，不复制 Web 账号密码登录逻辑。
- 通过云函数执行授权、导入和跨集合操作。
- 第一期开启班级、学生、考勤和表现记录能力。

### 7.3 冲突规则

以下数据禁止静默覆盖：学生档案、成绩、考勤、表现记录、请假记录和家校沟通记录。

冲突报告至少包含：

```text
uuid
本地版本
云端版本
本地更新时间
云端更新时间
冲突字段
处理选项
```

保留全量恢复和追加导入的区别，让旧 JSON、当前 JSON 和 ZIP 都先经过预检；导入前创建快照，失败时回滚数据库和附件目录。

### 任务 5：建立 CloudBase 数据模型和权限

状态：基础阶段已完成。已创建教师、数据集、导入批次、班级和学生集合，五个集合权限均锁定为 `PRIVATE`；完整业务集合、索引和服务端授权规则在导入写库前继续补齐。

状态：预检阶段已完成。`import-data` 已部署并完成最小调用验证；真实分批写入、`sourceExportId`、`importBatchId`、幂等、失败重试和导入报告尚未开放。

### 任务 7：实现电脑端同步

### 任务 8：接入小程序工程与云函数

状态：基础阶段已完成。已创建微信项目配置、`miniprogram/` 和 `cloudfunctions/`，完成 CloudBase 连接适配，并部署 `query-data` 班级/学生只读函数；后续再做小程序页面、考勤、表现记录和 JSON 导入预检。不得把云函数实际代码放入 `cloudbase/` 配置目录。

## 九、测试门禁

### 9.1 兼容性

- v0.7.0 JSON 可以导入。
- 已承诺支持的历史 JSON 样本可以导入。
- v0.4.2 ZIP 可以在电脑端恢复。
- 旧版导入后再次导出，核心业务数据不丢失。
- 旧 UUID 在迁移前后保持不变。
- 不支持的格式版本被明确拒绝。

### 9.2 数据完整性

- 修改 JSON 一个字符后校验失败。
- 重复 UUID 被拒绝。
- 缺少父记录时拒绝相关子记录。
- 缺少必填字段时不写入半成品。
- 导入中断后不会留下未完成数据集。
- 重复 `exportId` 不会重复创建数据。

### 9.3 权限和回归

- 教师 A 无法读取教师 B 的数据。
- 客户端伪造 `ownerId` 不会越权。
- 普通教师不能调用管理员接口。
- 兑换码状态只能由服务端改变。
- `npm test`、`npm run version:check`、`npm run build` 和便携包 QA 继续通过。

## 十、验收标准

1. v0.7.0 是明确的当前开发基线。
2. v0.8.0 可以继续导入历史版本软件导出的 JSON 和 ZIP 数据。
3. JSON 交换格式有永久兼容策略和明确迁移器。
4. SQLite 本地迁移和 JSON 交换迁移互相独立。
5. UUID 不因版本升级被重新生成。
6. 客户端导出的结构化数据可以进入 CloudBase。
7. 小程序可以读取导入后的班级和学生数据。
8. 电脑端和小程序使用同一套云端记录身份。
9. 附件暂不上传，但附件元数据不会破坏业务记录导入。
10. 导入失败、冲突和权限异常都有可诊断结果。

## 十一、执行前提

正式实施前需要确认：

- 云端首次导入默认创建新数据集；
- 同一教师账号下学号是否全局唯一；
- 电脑端首次使用云端功能是否必须联网；
- 教师账号是否只使用微信身份；
- 兑换码采用永久授权、按年授权还是按版本授权；
- v0.8.0 是否同时发布本地兼容升级和 CloudBase 导入 MVP。

在数据样本库、UUID 规则和导入回滚方案完成前，不开始完整小程序页面体系，不删除旧版导入代码，不升级 JSON `formatVersion`，也不直接覆盖线上云端数据。
