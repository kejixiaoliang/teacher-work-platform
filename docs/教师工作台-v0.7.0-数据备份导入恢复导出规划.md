# 教师工作台 v0.7.0 数据备份、导入、恢复与导出规划

> 文档性质：数据工程与版本兼容基线  
> 适用版本：v0.7.0 及后续版本  
> 编写依据：当前 v0.7.0 代码审查、现有备份实现、v0.6.0 访问控制实现，以及《教师工作台 JSON 备份交换格式 v1 规范》  
> 最后更新：2026-08-25

## 1. 文档目的

数据备份不是一个普通的“下载按钮”功能，而是教师工作台在换电脑、升级软件、数据恢复、旧版本迁移和未来云端导入时的基础设施。本规划用于统一以下内容：

- 什么数据必须导出，什么数据必须排除；
- JSON 导出、完整 ZIP 备份、恢复和更新导入之间的区别；
- v0.5、v0.6 等旧版本数据如何进入新版本；
- 附件、数据库记录和记录之间的关联如何保持；
- 密码保护、教师工作台模式和班级公开模式如何与备份隔离；
- 恢复失败时如何回滚，导入前如何预览和发现风险；
- 如何通过自动化测试确认“完整备份没有遗漏”。

本文是实施规划，不等同于已经完成的功能。代码必须以本文确定的模型和验收标准为准，不应继续直接扩展现有的数据库表快照逻辑。

## 2. 当前实现审计结论

### 2.1 已有能力

当前 v0.7.0 分支已经具备以下基础：

- 服务端可以导出全量 ZIP；
- ZIP 中包含 `backup.json` 和 `files/` 附件目录；
- 当前导出包含 18 张业务表；
- 恢复前会创建数据库快照；
- ZIP 附件会进行大小和 SHA256 校验；
- 恢复过程使用数据库事务，并执行外键检查；
- 当前分支已经有教师密码、教师工作台模式和班级公开模式；
- 现有测试覆盖了部分 ZIP 创建、附件恢复和工作流恢复场景。

### 2.2 主要问题

当前实现仍然是“当前数据库结构的复制”，还不是稳定的数据交换系统。

#### 问题一：现有内部格式与正式 JSON v1 规范不一致

当前格式类似：

```json
{
  "app": "teacher-work",
  "version": 2,
  "tables": []
}
```

正式交换格式则应包含：

```json
{
  "format": "teacher-work-backup",
  "formatVersion": 1,
  "appVersion": "0.7.0",
  "databaseVersion": 6,
  "exportId": "...",
  "source": {},
  "content": {},
  "attachments": {},
  "integrity": {}
}
```

两者不是简单增加几个字段，而是“数据库表结构”与“业务交换模型”的区别。新版本不能只根据 `version` 字段猜测格式，必须建立明确的格式识别器和迁移器。

#### 问题二：旧版导入严格依赖当前表结构

当前恢复逻辑要求备份包含当前版本的全部表，并且记录字段必须能够被当前数据库识别。旧版缺少新表或新字段时，可能被直接拒绝；字段重命名也没有统一迁移层。

因此，“数据库迁移”与“备份文件迁移”必须分开：

- 数据库迁移：本机旧数据库启动时升级表结构；
- 备份迁移：新版本读取旧版 ZIP/JSON，转换为统一业务模型。

#### 问题三：业务关系依赖本地自增数字 ID

当前记录主要通过 `class_id`、`student_id`、`exam_id` 等数字 ID 建立关系。数字 ID 只在单个数据库内有意义，不适合作为跨版本、跨设备的长期身份。

例如旧电脑的 `student_id=12` 与新电脑的 `student_id=12` 不一定是同一名学生。直接复制数字 ID 会导致关联错误或导入冲突。

#### 问题四：没有真正的 JSON-only 导出

现有入口主要导出 ZIP。虽然恢复入口可以读取部分旧 JSON，但这不等于已经实现了符合规范的 JSON 交换文件。JSON-only 文件必须具备格式版本、完整性校验、附件省略说明和稳定关系信息。

#### 问题五：班级备份和完整备份的恢复语义不清晰

当前班级备份可以只导出一个班级，但恢复逻辑仍可能覆盖整个工作台。这会让教师误以为“导入一个班级”，实际却可能删除当前其他班级数据。

后续必须明确区分：

- 完整恢复：替换整个工作台；
- 班级导入：把一个班级更新或新增到当前工作台；
- 数据更新：按稳定 UUID 更新已有记录，不删除备份中不存在的数据。

#### 问题六：访问控制配置不能直接随业务数据恢复

`app_settings` 中包含访问模式、密码摘要、密码盐、恢复密钥摘要等安全配置。完整复制该表会带来安全风险，完全忽略该表又可能遗漏未来的业务设置。

解决方案是建立导出白名单：业务设置可以导出，安全设置永不导出。恢复后保留当前设备的教师密码、当前模式和访问策略。

## 3. 总体设计原则

### 3.1 JSON 是业务交换格式，ZIP 是传输容器

JSON 描述业务数据和附件关系；ZIP 只负责把 JSON 与附件放在一起传输。不能把 SQLite 文件或当前表快照直接当作长期交换格式。

### 3.2 先识别格式，再迁移，再写入数据库

所有导入必须遵循：

```text
文件识别
  ↓
安全检查
  ↓
完整性校验
  ↓
格式迁移
  ↓
业务模型校验
  ↓
导入预览
  ↓
教师确认
  ↓
事务性写入
  ↓
结果审计
```

禁止直接把外部 JSON 映射到 SQL 表，也禁止导入过程中遇到缺失字段就静默丢弃。

### 3.3 旧版兼容必须显式、可测试、可追踪

每一种旧格式都要有独立的识别器、迁移器和测试样本。导入结果必须记录来源版本、来源格式和 `exportId`，方便排查。

### 3.4 默认安全优先

- 备份文件视为敏感文件；
- 密码、Token、恢复密钥原文和本地绝对路径永不导出；
- 完整恢复和更新导入只能在教师模式下执行；
- 班级公开模式只能查看允许公开的模块；
- 导入前必须预览，不能选择文件后立即覆盖数据；
- 恢复前必须保存当前工作台快照。

### 3.5 宁可明确提示不完整，也不能静默丢数据

如果附件缺失、字段被转换、旧版记录无法建立关系，系统必须显示数量和原因。可以允许“仅导入可恢复业务数据”，但不能把不完整结果伪装成完整恢复成功。

## 4. 统一数据模型

### 4.1 稳定 UUID

以下业务实体必须增加稳定 UUID：

- 班级；
- 学生；
- 考试；
- 成绩记录；
- 考勤记录；
- 请假记录；
- 学生跟进事项；
- 身高视力历史；
- 座位记录和座位布局；
- 文档元数据；
- 值日和班委记录；
- 家校沟通记录；
- 表现量化分类、项目、记录和修订记录。

本地数字 ID 可以继续保留，但只作为本地兼容字段和诊断字段。跨记录关系优先使用 UUID，例如 `classUuid`、`studentUuid`、`examUuid`。

### 4.2 旧记录补 UUID

旧版本没有 UUID 时，导入器应按以下规则处理：

1. 如果旧记录已有合法 UUID，保留原值；
2. 如果没有 UUID，为记录生成新的 UUID；
3. 使用旧表名和旧数字 ID 建立临时映射；
4. 通过映射重建所有外键关系；
5. 导入后再次导出时使用新 UUID，后续导入保持稳定。

不能用数组顺序、姓名或学号单独作为永久身份。姓名和学号只能用于冲突提示和人工辅助匹配。

### 4.3 敏感设置与业务设置分离

建议将设置分成两类：

| 类型 | 示例 | 是否导出 |
|---|---|---|
| 业务设置 | 默认学期、界面偏好、非敏感显示选项 | 可以导出 |
| 安全设置 | 密码摘要、密码盐、恢复密钥摘要、会话信息、Token | 永不导出 |

恢复备份后，当前设备的安全设置保持不变。这样既不会丢失密码保护，也不会通过备份复制安全凭据。

## 5. 三种文件和四种操作

### 5.1 JSON-only 导出

文件扩展名建议为：`.teacher-work.json`。

用途：

- 迁移业务数据；
- 上传到未来小程序或云端；
- 不携带附件的轻量备份；
- 版本兼容测试。

必须包含：

- `format`、`formatVersion`；
- `appVersion`、`databaseVersion`；
- `exportId`、`exportedAt`、`source`；
- 全部业务集合，即使为空也不得省略；
- `attachments.included=false` 和省略数量；
- SHA256 完整性字段。

### 5.2 完整 ZIP 备份

建议结构：

```text
教师工作台完整备份.zip
├── backup.json
├── manifest.json
└── files/
    ├── 文档附件 1
    └── 文档附件 2
```

`backup.json` 使用与 JSON-only 相同的业务模型，但附件字段标记为包含。`manifest.json` 保存文件相对路径、原始名称、大小、MIME 类型和 SHA256。

完整 ZIP 必须覆盖：

- 全部班级；
- 全部学生和学生历史；
- 全部成绩、考试和成绩关联；
- 全部考勤和请假；
- 全部表现量化规则、记录和修订记录；
- 全部座位、值日、班委和跟进事项；
- 全部家校沟通；
- 全部文档元数据；
- 文档元数据所引用的全部附件；
- 可迁移的业务设置；
- 数据统计和完整性信息。

### 5.3 恢复

恢复是破坏性操作，语义为“用备份替换当前整个工作台”。

流程：

1. 仅允许教师模式执行；
2. 读取并校验文件；
3. 展示班级、学生、成绩、附件等数量；
4. 明确提示会覆盖当前全部业务数据；
5. 创建当前数据库和附件目录快照；
6. 在临时区域完成迁移和完整性检查；
7. 在事务中写入数据库；
8. 校验外键、UUID 和附件关系；
9. 替换附件；
10. 成功后记录恢复日志并刷新页面。

任何步骤失败，都不能留下半恢复状态。

### 5.4 更新导入

更新导入不是恢复，不清空现有工作台。

默认策略：

- 同 UUID 记录：更新；
- 新 UUID 记录：新增；
- 当前存在但备份没有的记录：保留；
- 备份中标记为删除的记录：先进入冲突预览，不直接删除；
- 冲突字段：展示旧值、新值和来源，要求教师确认。

第一版可以先实现“导入为新班级/新数据集”，之后再实现复杂字段级合并。不能把“恢复”误称为“更新”。

## 6. 旧版本兼容策略

### 6.1 支持的历史输入

新版本至少应识别：

1. v0.5/v0.6 的旧版 ZIP；
2. 旧版 `app/version/tables` JSON；
3. v0.7 JSON v1；
4. v0.7 完整 ZIP。

不支持的文件必须明确提示格式版本，不得尝试猜测导入。

### 6.2 迁移器架构

```text
legacy-tables-v1 ─┐
legacy-tables-v2 ─┼─> 统一内部模型 ─> 当前数据库写入器
teacher-work-json-v1 ─┘
teacher-work-zip-v1 ──> 解包后进入同一条链路
```

每个迁移器必须负责：

- 字段重命名；
- 缺失字段默认值；
- 旧数字 ID 到新 UUID 的映射；
- 数据类型转换；
- 关系完整性检查；
- 附件元数据转换；
- 导入警告和统计。

### 6.3 缺失字段规则

可以安全补默认值的字段包括空备注、空标签、默认状态和可选显示字段。

不能擅自补成 `0` 的字段包括成绩、天数、金额、健康指标等。缺失时应使用 `null` 或空值，并在预览中提示。

### 6.4 旧版附件规则

- ZIP 中存在附件：校验后导入；
- JSON-only 没有附件：保留文档记录，标记为 `omitted`；
- 文档元数据存在但实际文件缺失：提示缺失数量；
- 缺少附件不应导致全部业务数据不可恢复；
- 如果用户选择“完整恢复”，则缺失附件应阻止最终确认，除非用户明确选择“仅恢复业务数据”。

### 6.5 版本兼容承诺

从 v0.7.0 开始：

- 当前版本生成的文件必须能被后续版本读取；
- 新版本至少兼容最近两个交换格式版本；
- 软件版本升级不必然导致交换格式升级；
- 只有结构、语义、关系或校验规则发生不兼容变化时才升级 `formatVersion`；
- 不支持的格式版本必须拒绝并说明原因。

## 7. 完整性与安全设计

### 7.1 JSON 完整性

使用规范化 JSON 计算 SHA256：

1. 复制完整对象；
2. 将 `integrity.value` 置为空字符串；
3. 对象键递归按 Unicode 字典序排序；
4. 数组保持原顺序；
5. 使用 UTF-8、无额外空格和换行序列化；
6. 计算 SHA256 并写回 `integrity.value`。

键顺序变化不应改变校验结果，内容变化必须导致校验失败。

### 7.2 ZIP 安全

解包必须防止：

- `../` 路径穿越；
- 绝对路径写入；
- 重复文件名；
- 超过文件数量、单文件大小和总大小限制；
- 伪造附件路径；
- 恶意压缩炸弹。

附件只能写入临时目录，校验完成后才能进入正式 `data/files`。

### 7.3 访问控制

- 班级公开模式不可执行完整备份、恢复和更新导入；
- 教师模式是执行数据操作的必要条件；
- 密码摘要、盐、恢复密钥、Token、会话信息不得进入 JSON 或 ZIP；
- 导入日志只记录 `exportId`、版本、结果和错误类型，不记录完整学生数据；
- 下载的备份文件必须提示其包含学生隐私和成绩信息。

## 8. 数据完整性审计机制

为了保证以后新增模块不会被备份遗漏，不能只手工维护一个表数组。应增加“备份覆盖审计”：

### 8.1 数据库层审计

启动测试读取数据库中所有业务表，与备份注册表比较：

- 新增业务表必须明确标记为导出、排除或内部表；
- 未注册的业务表导致测试失败；
- `app_settings` 等敏感表必须通过显式排除清单审核；
- 每张导出表必须有对应序列化和反序列化测试。

### 8.2 关系层审计

导出后检查：

- 所有外键都能找到目标记录；
- 所有 UUID 在同类数据中唯一；
- 所有文档元数据引用的附件都有 manifest 项；
- 所有附件 manifest 项都能找到文件；
- 所有班级、学生、考试和成绩关系可重建。

### 8.3 往返审计

测试流程必须包含：

```text
创建完整样例数据
  ↓
导出 JSON / ZIP
  ↓
导入到空数据库
  ↓
再次导出
  ↓
比较核心数据、关系、附件哈希和统计结果
```

不能只比较文件文本，因为导出时间、导出 ID 和数据库本地 ID 可能变化。应比较规范化后的业务内容和关系结果。

## 9. 界面和使用指南规划

“数据管理”区域应明确提供：

- 导出 JSON；
- 下载完整 ZIP；
- 恢复完整 ZIP/JSON；
- 更新导入；
- 查看导入预览；
- 查看最近一次备份和恢复结果。

按钮文案不能使用含义模糊的“备份”或“导入”。应明确写成：

- `导出 JSON（不含附件）`；
- `下载完整备份（含附件）`；
- `恢复整个工作台`；
- `更新导入到当前工作台`；
- `导入为新班级`。

使用指南必须说明：

1. 教师工作台模式用于维护隐私数据和执行备份恢复；
2. 班级公开模式用于投屏或公开查看，只开放允许公开的模块；
3. 自动锁定后会回到班级公开模式；
4. 恢复不会覆盖当前设备密码；
5. JSON 不含附件，完整 ZIP 才包含附件；
6. 恢复会覆盖全部工作台，更新导入不会主动删除现有数据；
7. 升级软件前先导出 JSON 和完整 ZIP，并把文件复制到应用目录之外。

## 10. 实施阶段

### 阶段一：规范和审计基础

- 将 JSON v1 规范纳入当前 worktree；
- 定义统一内部模型；
- 建立业务表注册清单和敏感设置排除清单；
- 增加稳定 UUID 字段和旧数据补 UUID 迁移；
- 增加完整性、关系和附件覆盖测试。

### 阶段二：JSON-only 导出和导入

- 实现规范化 JSON；
- 实现 SHA256；
- 导出全部业务集合；
- 实现 v1 JSON 导入；
- 实现导入预览和事务恢复；
- 完成空数据、多班级、带附件元数据和旧字段样本测试。

### 阶段三：完整 ZIP 备份

- 以统一 JSON 为 ZIP 内部数据；
- 增加 manifest 和附件哈希；
- 支持附件完整恢复；
- 支持附件缺失时的“仅恢复业务数据”；
- 完成 ZIP 路径安全和压缩限制测试。

### 阶段四：旧版兼容

- 编写旧版 tables JSON 迁移器；
- 编写 v0.5/v0.6 ZIP 迁移器；
- 增加缺表、缺字段、字段改名和旧附件测试样本；
- 导入后检查关系和数据统计；
- 在指南中列出支持的历史版本。

### 阶段五：更新导入

- 支持按 UUID 新增和更新；
- 提供冲突预览；
- 默认不删除当前数据；
- 支持导入为新班级或新数据集；
- 记录导入任务和重复 `exportId`。

## 11. 验收标准

### 导出

- 空数据可以导出；
- 多班级、多学生和全部模块数据都存在；
- JSON 的所有集合字段始终存在；
- 不包含密码、Token、恢复密钥和绝对路径；
- 附件省略数量准确；
- 完整 ZIP 中每个附件都有 manifest 和 SHA256。

### 导入和恢复

- 正确 JSON/ZIP 可以导入；
- 修改一个字符后完整性校验失败；
- 不支持的格式版本被明确拒绝；
- 缺少可选字段可以使用安全默认值；
- 旧版本数据可以导入并保持核心关系；
- 恢复前自动快照当前工作台；
- 导入失败不改变当前数据库和附件；
- 恢复后当前密码和访问模式仍然有效。

### 更新

- 同 UUID 记录能够更新；
- 新 UUID 记录能够新增；
- 当前已有但备份没有的记录不会被默认删除；
- 冲突有明确预览；
- 重复 `exportId` 能被识别。

### 回归

- 成绩、考勤、请假、量化、沟通、跟进、座位和附件均有往返测试；
- v0.5/v0.6 真实样本可以导入；
- 导入后再次导出，核心业务数据保持一致；
- 备份覆盖审计能发现新增但未注册的业务表；
- 教师模式和班级公开模式的操作权限符合指南说明。

## 12. 最终决策

v0.7.0 的数据工作不应继续围绕“把现有表完整复制出来”展开，而应完成以下转变：

```text
数据库快照
    ↓
统一业务模型
    ↓
带版本、校验、UUID 和迁移器的数据交换格式
    ↓
JSON 导出、ZIP 完整备份、恢复和更新导入
```

只有完成这一层，教师才可以放心地换电脑、升级软件、恢复误删数据，并把旧版本数据带入新版本。数据完整性、旧版本兼容和恢复回滚应优先于界面美化和新增零散功能。
